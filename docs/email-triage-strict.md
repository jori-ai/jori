# Strict email triage

Per-message Gmail triage reads mail from anyone. Until 2026-11-16 every such email became a turn in the ops-light session: Sonnet with Bash, files, the web, 66 Jori tools and a long-running session that also runs Hum and other jobs. An email that talked the model into something had all of that to work with.

The strict path triages the same email, under the same Email Triage Rules, in a one-off `claude -p` that has no shell, no files, no web, no browser and no mailbox search. It runs when the target is `"strict"` (the kernel's `agents.json` → `ops.gmailTriageTarget`, or an installation's own `gmail_triage_target`).

## Pieces

| Piece | What it does |
|---|---|
| `agent/supervisor/triage-route.mjs` | With `"strict"`, runs the one-shot for each per-message item (at most `STRICT_MAX` = 3 at once). When it does not finish, the item goes to ops-light as before, with a note of what the one-shot already did. Each run leaves a marker in `data/triage-strict-pending/` until it ends; a marker older than 11 minutes (the supervisor restarted mid-run) is dispatched to ops-light once. With `"strict-shadow"`, triage stays on ops-light and a dry one-shot runs alongside each item. |
| `bin/email-triage-report` | Scores the shadow runs against the decision record (`triage_decisions`). |
| `bin/email-triage-run` | Starts the one-shot: built-in tools off (`--tools ""`), `--strict-mcp-config` to one server, Sonnet at medium effort, the locked-down agent environment (`lib/agent-env.cjs`, id `email-triage`). Exit 0 = triaged or escalated; exit 3 = fall back. Log `data/email-triage-oneshot-log.jsonl`; cost rows in `agent/logs/ephemeral-forks/job-costs.ndjson` under `gmail:<id>`. |
| `agent/tools-mcp/email-triage.mjs` + `lib/email-triage-tools.mjs` | The only tools. Each wraps the CLI the rules name, so the rules read the same. |
| `agent/ops-agent/jobs/email-triage-strict.md` | The one-shot's system prompt (the `oneshot` section): which tool stands for which command, and "no tool → escalate". |

## Bounds, enforced in code

- **The email is bound by the runner** (message id, sender, subject, Date). Gmail changes, the P1 task, the P1 downgrade and the spam block act on that email or sender only; no tool takes a message id or an address.
- **Labels** come from the triage label set plus `p1`/`p3` (and an installation's `email-triage.json` `extra_labels`).
- **`notify_owner`** reaches the owner only, with an intent from a fixed list; `--evidence-as-of` is the email's own Date and a P1 pointer carries `--p1-message`. The send still passes the precheck and the speak gate.
- **Calendar writes** take no attendees.
- **`escalate_to_ops`** sends ops-light (never the ops tier, which carries Chrome) the message id, a reason from a fixed list, a validated rule slug and, in code's own words, what the run already changed; never model-written text. Ops-light re-reads the email itself, so an escalated email is still read by a Bash-capable agent: this narrows the exposure, it does not remove it.
- **Nothing changes before the whole rules core is read.** Every tool that changes something, and `escalate_to_ops`, refuses until the run has read every page of `triage_rules core` (2026-11-23: five shadow runs had read only part of it, and one of them filed a P1 security alert P3).
- **A standing P1 cannot be undone.** When intake stamped the email P1 by a rule the triage rules make final (the P1 sender list, a reply to something the user sent, a meeting request; `STANDING_P1_STAMPS`), `p1_downgrade`, `unstar`, `unlabel p1` and `label p3` are refused. The runner reads the stamps off the dispatch's own `Intake stamps:` line (`intakeStamps`) and passes them to the tool server (`TRIAGE_STAMPS`). (2026-11-23: five of the shadow week's eight missed P1s were the one-shot undoing such a stamp.)
- **`sender_recent`** shows the sender's own mail of the last two days from the triage record (arrival time, label, priority; no ids, subjects or bodies), and **`own_signins`** the agent's own sign-in attempts at the sender's site in the three hours before the email was sent (`lib/login-log.cjs`: time, outcome, which job), so a burst of security alerts can be told apart from the agent signing in, without a mailbox search.
- **A change counts only once it succeeded.** Each changing tool runs, then records its outcome; a failed call is recorded as failed. The runner falls back (exit 3) when nothing succeeded or the escalation failed.
- **No tool** for following links, the browser, the Gmail connector, a reply or forward, a dispatch, or an installation's own commands: each is an escalation.

## What escalates

Measured over 933 ops-light triage turns (2026-10-18 to 11-16), 87.5% used only commands this toolbox covers. The rest are mostly Amazon delivery tracking (following the tracking link, four times opening an Amazon order page in the signed-in browser), the Gmail connector for the thread, and an installation's own commands (TripIt forward, the property-portfolio CLI, show and comedian logs). Those now escalate to ops.

## Rollout

1. **Replay (dry run, by hand).** `email-triage-run --payload <p> --dry-run` runs the read tools and records every change it would make. Replaying recent emails and comparing the labels, priority, pings and tasks with what the ops-light turn did is the evidence for the flip.
   **First replay, 2026-11-16** (30 random ops-light triage emails from Nov 9–16, the decision record as ground truth after the resolution repair): 29 of 30 finished (the 30th triaged correctly with a task and a ping but no label change, which the runner then counted as a failure; fixed). Against the recorded decision, the label matched 26/29 and the priority 25/29. The priority differences: two lease-date notices and one application notice the one-shot filed P3/P2 by the email memory where the agent had left intake's P1, and one Zoho Sign bounce it judged a duplicate using memory written after the email (a replay artefact). P1 pings and P1 tasks matched the agent's on 28/29. 6 escalated (4 Amazon "Delivered" mails, which need the order page; a car-rental confirmation, which needs the TripIt forward and flights-scan; one thread question). **These numbers came from runs that saw only part of the rules core** (the 53 KB result was moved to a file the one-shot cannot open; fixed the same day by paging), so they are not evidence. With the whole core read, a run costs about $0.17 and 13 s, close to an ops-light triage turn (about $0.16).
   A replay is weak evidence: the tools read today's Gmail labels and email memory, which the agent wrote when it triaged that same email (11 of the 30 runs read the memory, and the Apple Support run skipped a calendar event because the agent's own event was already there).
Where the mode is set: the installation's `agent/local/config/agents.json` `gmail_triage_target` (over the kernel's `ops.gmailTriageTarget`). The router re-reads it on each email (cached 30 s), so a change, including a rollback to `"ops-light"` or `"ops"`, takes effect without restarting the ops supervisor.

2. **Shadow** (2026-11-16 to 11-23). `gmail_triage_target: "strict-shadow"`: live triage unchanged, and a dry one-shot ran on each email as it arrived, before the agent had written anything about it. `bin/email-triage-report` scores the runs at least 20 minutes old against the decision record. The bar it prints is the one the triage rules set for replacing triage (≥ 150 scored emails over ≥ 7 days, label and priority agreement ≥ 95%, zero missed P1s); escalated runs are counted, not scored.
   **The week, scored 2026-11-23** (`email-triage-report --days 8`): 327 runs, 212 scored, label agreement 81.6%, priority 91.0%, 8 missed P1s, 49 escalated (15% of the runs), no fallbacks, 64 with no recorded decision (the live agent left no triage label: an off-list label such as `finance` or `travel`, or none on an intake P1), 5 that read only part of the rules core. Each disagreement was traced to the agent's own turn in the ops-light event log:
   - **Missed P1s.** Five were the one-shot undoing a standing intake P1 (two payments-partner marketing mails and two notices from the user's own business platform, all on the P1 sender list, a board-meeting reminder stamped as a meeting request): fixed in code (the standing-P1 guard above). One was a run that skipped part of the core and filed a first-time Google account-access alert P3: fixed by the core gate. The other two were the live agent judging from more than one email. One was right: a board agenda whose Zoom link and time belonged to another building's meeting, now a kernel Step 4 rule ("an email that contradicts the calendar"). The other was the live agent's own false alarm: a third new-device alert in three minutes that it pinged about, when the agent's own sign-in attempts at that site, two minutes before each alert, explained all three (the sign-in log); the shadow's P2 was the better call. Repeated security alerts that the agent's own sign-ins do not explain are now a Step 4 rule, with `sender_recent` and `own_signins` to check it.
   - **Labels.** Most were property mail (a renovation, a condo board, a property's insurance and power bill) that the one-shot filed under the wrong label: it sees the triage rules, not the property table in the agents' own system prompt. The installation's rules now say what each label covers, with the property names and addresses, and that a Zoom call summary takes the call's label. The rest were `personal` against `vendor` where the one-shot overrode a settled sender history; its prompt now lets a settled history decide a choice the rules leave open.
   - **Agent errors.** Several priority differences were the live agent's (a first-time subscription and a booking receipt the rules make P1 that it filed P2/P3; two alerts it called P2 but never starred). No user reclassification changed a scored email's outcome.
   **Replay after the fixes** (`email-triage-run --dry-run`, payloads rebuilt from the dispatch text): the 8 missed P1s and 14 label disagreements re-run, plus 6 emails the shadow had matched. 6 of the 7 real missed P1s now come out P1 (the false-alarm one, re-run with `own_signins`, is left below P1, as it should be); the seventh (the agenda) is moot in a replay because the meeting is over, so a synthetic agenda for a meeting still ahead, with another time and link, was run instead and came out P1 with a ping naming both versions. 13 of the 14 labels now match (the 14th is a Zoom summary the live agent itself labelled unlike its other ones), and all 6 matched emails still match. Every run read the whole core. A replay is still weak evidence (it reads today's labels and email memory). After the switch there are no shadow runs: live runs are logged as `mode: "live"` in the same file, and `email-triage-report` (which scores only shadow runs) has nothing new to score; to measure again, go back to `"strict-shadow"` for a while.
3. **Switch** (2026-11-23). The user's instruction (2026-11-16): run the shadow a week, then review, fix and switch. With every missed P1's cause fixed and escalations at about 15%, `gmail_triage_target` is `"strict"`: each per-message email runs the one-shot, and goes to ops-light only when the one-shot does not finish (exit 3) or escalates. The router re-reads the setting on each email, so it took effect without a restart. Rollback: `"ops-light"` (or `"strict-shadow"` to go back to scoring without acting).

`triage-decide` (decide-then-act in code, `email-triage-rules.md` § Decide-then-act) is a separate path that runs before dispatch; when it goes live, the strict one-shot covers what it still hands to an agent.
