# Secrets broker

The agents run as the same macOS user as everything else, so any key in a file or process of that user is one command away from them. The secrets guard (`docs/agent-secrets.md` § 2) catches the plain reads, but not one that builds the path in pieces (`f=.e; cat ${f}nv`) or one that loads `.env` through the repo's own loader. Only a key that user cannot read is out of reach. The broker is that: a small server running as its own user, `_jorisecrets`, holding keys that no process of the agents' user can read. It answers a fixed set of requests and never returns a key.

## Stage 1: the 1Password tokens

`OP_SERVICE_ACCOUNT_TOKEN` (the Dev vault) and `OP_LOGINS_SERVICE_ACCOUNT_TOKEN` (the Logins vault) live in the broker. The helpers that used them ask the broker instead:

| Helper | Request | The broker allows |
|---|---|---|
| `bin/site-pass` | `logins.list` (Login), `logins.login_field` | the Logins vault's overview (no secret field); username or password of a Login item none of whose URLs is a money-movement site |
| `bin/card-pass` | `logins.list` (Credit Card), `logins.card` | cards tagged with the policy's purchase tag only |
| `bin/dev-pass` | `dev.site` | the Dev item titled `site:<domain>`, never for a money-movement domain |
| `bin/sms-send` | `dev.item` `sms-send` | the Twilio item's listed fields only |

There is no generic read: no `op read` of an arbitrary reference, no other vault, no write. Every read that returns a value counts against an hourly cap (`rate.per_hour`, 120). Every request is appended to `/Library/JoriSecrets/log/audit.jsonl` (operation, item, field, result; never a value), which the agents' user can read but not change.

What it does **not** stop: an agent can still read, through these helpers, the logins and cards they reach today. What it stops is taking a token, which reads the whole vault from anywhere until it is revoked, and writes. The gain lands once the old tokens are revoked: until then a copy in `.env`, a backup or a log is still good.

Not routed, and left to fail once the tokens leave `.env` (all bootstrap paths, run when a key is missing): `bin/zoom-probe --install`, the `op` fallbacks in `bin/flight-search`, `bin/findme`, `bin/location-segment`, `bin/supabase-token`. `bin/logins-import-apple` writes to the Logins vault; it runs by hand from the MacBook with the 1Password app, and the writer token `OP_LOGINS_WRITER_TOKEN` is revoked, not moved.

## Pieces

| Piece | Where | Owner |
|---|---|---|
| `lib/secrets-broker/broker.cjs` | the server; node's standard library only | copied to `/Library/JoriSecrets/lib`, root |
| `agent/local/config/secrets-broker-policy.json` | the policy, generated by `bin/secrets-broker-policy` from the helpers' own sources (the denylist in `credential-denylist.sh` + `credentials.json`, the vault names, `purchase.json` `card_tag`, `sms-send.json`) | copied to `/Library/JoriSecrets/etc/policy.json`, root |
| `bin/secrets-broker-install` | the installer, run with sudo from the staging directory | `/Library/JoriSecrets/staging`, root |
| `bin/secrets-broker`, `lib/secrets-broker/client.cjs` | the client; holds nothing | the checkout |
| `/Library/JoriSecrets/bin/{node,op}` | copies, checked by code signature after copying (Node.js Foundation `HX7739G8FX`, AgileBits `2BUA8C4S2C`) | root |
| `/Library/JoriSecrets/store/secrets.json` | the keys | `_jorisecrets`, 0600 in a 0700 directory |
| `/Library/JoriSecrets/run/broker.sock` | the socket, open to every local process | `_jorisecrets` |
| `/Library/LaunchDaemons/com.jori.secrets-broker.plist` | runs `node broker.cjs --root /Library/JoriSecrets` as `_jorisecrets`, kept alive | root |

`/Library` is root's alone, so the agents' user cannot rename or replace anything under it, as it could under `/Library/Application Support`. The broker reads only root-owned files and its own store. It runs `op` with one token and nothing else in its environment. It treats every request as coming from an agent: a socket's caller cannot be told apart from an agent.

## Install

Root must never run or copy anything the agents can change: the checkout, `~/.local/node` and Homebrew's `op` are all writable by the agents' user. So the user copies the three files into root's staging directory, checks their SHA-256 against the hashes given in the session, and runs the installer from there. The installer copies `node` and `op` itself and checks each copy's signature. It reads `.env` as data, never sources it, and stores only the named keys.

```bash
sudo mkdir -p /Library/JoriSecrets/staging
sudo install -o root -g wheel -m 755 ~/Dev/jori/bin/secrets-broker-install /Library/JoriSecrets/staging/
sudo install -o root -g wheel -m 644 ~/Dev/jori/lib/secrets-broker/broker.cjs ~/Dev/jori/agent/local/config/secrets-broker-policy.json /Library/JoriSecrets/staging/
sudo mv /Library/JoriSecrets/staging/secrets-broker-policy.json /Library/JoriSecrets/staging/policy.json
shasum -a 256 /Library/JoriSecrets/staging/*        # compare with the hashes you were given
sudo /Library/JoriSecrets/staging/secrets-broker-install --install --env ~/Dev/jori/.env --import OP_SERVICE_ACCOUNT_TOKEN,OP_LOGINS_SERVICE_ACCOUNT_TOKEN
```

Then, once `jori doctor` shows `secrets broker answers` and the helpers work through it:
1. Remove both tokens and `OP_LOGINS_WRITER_TOKEN` from `.env`.
2. Rotate: in 1Password, create new service accounts, give each to the broker with `sudo /Library/JoriSecrets/staging/secrets-broker-install --set OP_SERVICE_ACCOUNT_TOKEN` (the value on stdin) and the same for `OP_LOGINS_SERVICE_ACCOUNT_TOKEN`, then revoke the old three. The new Dev one should see a small vault holding only the `site:*` items and the Twilio item, not the whole Dev vault. That way a mistake in the policy cannot expose the rest.

Changing the broker or its policy repeats the staging copy, the hash check and `--update`. Off: `sudo /Library/JoriSecrets/staging/secrets-broker-install --uninstall` (the helpers then fall back to `.env`, which by then has no token).

## Checks

- `jori doctor` → `secrets broker answers`: it answers, holds both tokens, and warns while `.env` still has a copy.
- `bin/secrets-broker health`: the tokens it holds (names only).
- From the agents' user: `ps eww <broker pid>` shows no environment, and `cat /Library/JoriSecrets/store/secrets.json` is refused.

## Next stages

One group at a time, each key rotated once it moves. The bank feed (Plaid), the database (Supabase service role), Slack, iCloud. Those are HTTP APIs: the broker takes the request without the key, checks its host against the key's own site, adds the key and makes the call. `gog`'s keyring password and the IMAP password cannot be added to a request that way, so the broker runs those commands itself.
