## The confirmed-fact backbone (2026-06-28 reframe — the user)

The 2026-06-27 summary shipped three errors at once, all the same root cause: **GPS gives WHERE a cluster was, but the venue NAME was an OSM/Google nearest-POI GUESS — and the narrator dressed guesses up as fact.** It named a 2-GPS-sample lunch "Nom Wah Tea Parlor, the century-old dim sum room" when the user had said in chat *"we went to Ping's, very disappointing"*; it narrated a Keith-Haring gallery VISIT that was only a recommendation ping (GPS had the user home); and it asserted a "Stonewall Inn, eve of Pride" stop whose only alternatives were "55 bar" and "Starbucks". Meanwhile the genuinely CONFIRMED signals went unused.

The fix inverts the trust order. The deterministic builder (`lib/daily-summary-confirm.js`, run inside `daily-summary-build prep`) computes a **provenance tier** for every stop's venue, and the H3 shows that certainty at a glance. As of 2026-07-27 the tier also produces the stop's **settled `title` + `title_certainty`** in the day JSON, and the renderer only formats those — so the table below describes what the JSON decides, not what the formatter guesses:

| Tier | Established by | H3 renders | Narrator may… |
|---|---|---|---|
| **CONFIRMED** | home/known-recurring, an in-person card charge, OR a chat statement the AGENT vetted | **bold name** | assert the name freely |
| **CORROBORATED** | an OSM/Google guess that AGREES with ≥1 independent signal | **bold name** | assert plainly, no embellishment |
| **GUESS** | OSM/Google, single signal, decent GPS; or an honest neighborhood label | muted `name · likely` (neighborhoods plain) | hedge: "around X" |
| **WEAK_GUESS** | ≤2 GPS samples, OR ≥2 near-equidistant alternatives, OR `browse` | `~name? · unconfirmed (also: A, B)` | hedge HARD, name the alternatives, **never** add encyclopedic colour |
| **GUESS, probable** (2026-10-22) | an unanswered "where was this?" card's default (`place.source: default_applied`, provenance `probable: true`): the hourly `choice sweep` applied it to that card's own row because the user never tapped | `probably name` | say "probably X" and nothing that assumes it; it stays a follow-up candidate, and the user's answer replaces it |

**Above all four: a window the user already answered as a non-stop (2026-07-27).** When the user replied to a location-enrich ask with "not a stop" / "we were walking along the coastline in the minimes park", `findme` stamps that visit row `place_type='non-stop'` (keeping the user's words as `place_name` when the user gave any) and `resolve-day` marks the stop `user_non_stop`. The builder renders those windows as `<the user's words>`, or `<area> · not a stop`, or plain `not a stop` — **never** a POI and **never** alternatives, and `place_name` in the manifest reads `not a stop` rather than the dropped guess. Your prose describes the movement ("not really a stop — you and Sam were walking the coastline through the park"), never a venue, and these windows are **not** follow-up candidates in Step 5.

**A guess belongs in a title only where no answer exists.** The user said it after the 2026-07-26 summary titled a stretch `~L'Équinoxe? · unconfirmed (also: Domino's, Le Transat)` while the prose right below it said *"Not really a stop, you and Sam were walking the coastline through the park"* — the user had answered that exact ask hours earlier. **If you know where the user was, the header must say so; if the header hedges, you must not know.** The two are the same fact, so before writing prose for any hedged stop, go find the answer (Steps 3c-3d) rather than writing around the header. If you end up writing prose that states a location for a `GUESS`/`WEAK_GUESS` stop, that is proof you owed a `--confirmed` entry (or that the stop is a `user_non_stop` the resolver missed) — fix it and re-prep; do not ship a header and a body that disagree.

**The two confirmed-fact sources, in priority order — this is the backbone:**
1. **User feedback in chat.** What the user volunteered ("we went to Ping's", "X was disappointing") or answered to a location-enrich question. The builder surfaces these as `chat_venue_candidates[]` (advisory — see Step 3c); a vetted one CONFIRMS its stop.
2. **In-person card transactions + GPS coordinates.** A card charge at an in-person merchant names the stop it sits in; mobility taps (MTA/tolls/rideshare) confirm travel mode. GPS coordinates anchor every stop's existence.

(**Photos are NOT a confirmation signal — they are embedded into the email and never interpreted.** See Step 3b. A stop is confirmed by chat + transactions only; its photos ride along in the email regardless of whether the venue got named.)

**Calendar + transactions REINFORCE — they don't drive.** A calendar event only corroborates a stop when `calendar_event.corroborated` is true (its location independently agrees with the GPS-resolved place, or a chat/txn confirmation already names the same thing) — plain time-overlap does not; a standout purchase weaves into a stop's prose. Neither invents a stop. (Who was with the user is a different question, and there the calendar does speak: Step 3e.) **A recommendation is NEVER a visit** (see Rules of the road).

## Rules of the road

- **GPS is the spine of the day.** The narrative timeline is built EXCLUSIVELY from `resolved.stops[]` (GPS-derived visits). Calendar events ANNOTATE GPS visits — they never become visits themselves. The email is primarily about WHERE the user was; everything else (calls, emails, commits, tasks) hangs off the visit it occurred during.
- **Venue identity is gated by provenance tier (2026-06-28).** Each stop in the manifest carries `provenance.{tier, hedge, confirmed_name, alternatives, sentiment}`. Your prose language MUST match the tier (table above): bold-asserted only for CONFIRMED/CORROBORATED; "around/looked like" for GUESS; hard hedge + alternatives for WEAK_GUESS. **Never add encyclopedic detail ("century-old dim sum room", "the eve of Pride") to a stop that isn't CONFIRMED** — that is exactly the 2026-06-27 failure. The H3 is already rendered by tier; the prose must not contradict it (don't assert in prose what the header hedges).
- **A recommendation is never a visit.** An assistant *recommendation ping* ("Keith Haring at Martos — about 100 min from now"), a `transparent`/free calendar event, or any "you could go to X" suggestion is NOT evidence the user went. Only a GPS stop (optionally corroborated by a matching calendar event / transaction / photo) is a visit. If GPS shows the user elsewhere (home) during the recommended window, the user didn't go — never narrate the rec as a visit. (The 2026-06-27 Martos fabrication.)
- **Mobility taps confirm travel mode.** `manifest.mobility[]` lists transit/toll/rideshare/parking/fuel charges (e.g. a $3 MTA tap). Reflect them in the relevant travel leg's framing ("took the subway down") instead of guessing or inventing a mode. They are NOT purchases — never render them as spending.
- **GPS always wins on conflict.** If GPS shows the user at place A at time T and the calendar says the user was at place B at time T, GPS wins. The calendar entry can be mentioned ("Calendar said B; GPS shows A — probably ran late / skipped / done remotely") but it does NOT override the visit's `place.name`.
- **Calendar without GPS evidence is NOT a visit.** Events with no overlapping GPS stop come through `resolved.unmatched_calendar_events[]` and go in the bottom "Events not matched to a location" section ONLY. Never put them on the timeline as if they were stops. (The one calendar event the timeline carries is a call, and only as code's own call line, never a stop: § Calls.)
- **A stop's prose narrates only that stop — never a neighboring stop or an unmatched event.** Two distinct events minutes apart in time or a few hundred feet apart in space — a restaurant next to a movie theater in the same shopping center, two errands in one plaza — stay two separate write-ups, never one merged story. Don't write a sentence like "From there into the movie…" inside a different stop's `<p>`, even when it reads naturally — that merges them in the reader's eyes exactly as much as a shared stop object would, and the user's rule is about the reading, not the JSON: *"I don't want the movie to be attached to the restaurant - I want them to be separate events, even if they're in a similar location."* An unmatched event stays confined to the "Events not matched to a location" section (below); it is never referenced from inside another stop's prose. If a genuinely shared physical stop ever needs one label for a dwell spanning multiple distinct venues, that label must come from the enclosing higher-hierarchy place (the mall/shopping-center/campus containing both venue points) — never a hand-picked name or the name of just one venue. See `feedback_day_segments_no_venue_event_merge` for the full design note; the hierarchy-lookup piece isn't built, so until it is, keep genuinely distinct venues as separate stops/events rather than inventing a shared label.
- **User-confirmed answers are absolute, even when not in `place.source`.** When `resolved.stops[i].place.source === "user_confirmed"`, that name is final — it came from the user directly answering "where were you?" Don't second-guess it, don't re-rank, don't suggest alternatives. (Resolver weight = 110, above named_location.) **AND** when the rendering subagent finds in the day's `jori_messages` transcript that the user gave a place name in reply to a location-enrich question whose `visit_id` matches a stop whose current `place.source` is a resolver-guessed one (`osm_overpass`, `google_places`, `reverse_geocode`, `coordinate`, `unknown`), the transcript-confirmed name MUST replace the H3 header's place name AND become the prose's primary venue. The user-confirmed name wins regardless of whether `chat-agent` successfully wrote it back to `location_history` via `findme resolve pending` — the conversation IS the source of truth, and the rendering subagent's job is to apply it. Do not preserve resolver guesses in the H3 with a "(actually X)" parenthetical; just use the confirmed name. (This rule was added 2026-05-02 after the 2026-05-01 daily summary shipped with osm-guess H3s — Haidilao, Asian Jewels, Starbucks, Vol de Nuit, Groove — when chat had already confirmed Y Space BBQ, Flushing supermarket, Patel Brothers, Greenwich Village Comedy Club, and Blue Note.)
- **A walk from the base is a slot; a walk to a named place is not.** When a stop carries `excursion`, the walk IS the entry and gets its own prose — it is not "how the user got to the next thing". When a stretch out and back contains a named stop, the named stop is the entry and the walk is only the travel line between blocks; do not write the walk up twice or promote it over the place the user went to. `excursions[].reason` tells you which case a given stretch was.
- **Never fabricate a stop.** Every place-mention in the narrative MUST correspond to an entry in `resolved.stops[]`. If no stop supports an activity, drop it (never "no GPS evidence" / "didn't capture" in a stop's prose, see the GPS-silence rule in 4.2).
- **Never re-date a correction.** `resolved.corrections[]` lists retroactive meta-signals the user sent; the narrator surfaces them in a "Corrections & follow-ups" section at the bottom as **questions**, not declarative facts about the target day.
- **Never dump raw self-sent iMessage text.** `day-statements` already has a model classify those (and `resolve-day` sorts its reading) — only `resolved.declarative_self_messages[]` are candidates for inclusion, and even then only when they clearly add context to a specific stop.
- **Travel mode comes from the spine, not from you.** See Step 3 — the spine leg's `mode` (and `mode_candidates` when uncertain) is the authority; e-scooter / micromobility evidence arrives as a `mobility[]` tap. If ambiguous, say "traveled X min" — don't force a mode.
- **Every matched photo appears inline** in its visit block, capped at 3 per block (favorites > non-screenshots > diverse media). Photos come from `resolved.stops[].photos`, not a separate harvest. **Each photo is on exactly one stop, the one it was taken at, and that stop's time covers it (2026-10-22):** `resolve-day`'s `pinStopsToPhotos` moves a stop's arrival back (or departure on) to a photo whose GPS puts it there, so a place is never reached after its first photo, and `settleStopPhotos` runs last so no photo sits under a stop whose window does not hold it, or under two stops. Neither moves a photo onto a stop the email does not draw (the renderer's `isMainStop`). What they did is on the day as `stops_pinned_to_photos[]` / `photos_settled[]` (context, never prose).
- **Standout purchases, woven in — not listed.** The builder surfaces the day's standout `plaid_transactions` (bank data) attached to the stops that generated them. Weave each into that activity's prose ("had lunch at Semma and spent $120"); never render a separate spending section. Bank data is jori-model-only and may render ONLY into this self-addressed email — never into a connector call (see Step 4.1 + CLAUDE.md § Financial Operations rule 5).
- **Read-only** on every source except `daily_summaries` upsert + temp HTML + outbound email + the single phone-channel ping at the end. (`plaid_transactions` is read-only, fetched locally by the builder.)
- **Budget.** 4 min wall-clock, 15 tool calls, one email, one phone ping, plus the questions of Step 4.7 (asked before the email, never after it).
- **Display time = the day's local time.** The day WINDOW (which UTC span is "date X") is midnight-to-midnight in the zone the day BEGAN in, read from the `travel` timeline (`lib/travel-timezone.js`: the `metro` slug first, a country in the label second; on a flight day, the zone the user started in), and every reader of the day uses that one window: resolve-day, `location-segment` (handed explicit instants, never bare dates, which it reads as home-zone days), the chat fetch and the harvest (`lib/day-window.js`). **Every day far east of home was once cut at midnight home time, i.e. 07:00 local** (the travel label was a street address that names no country, so it fell back to the home zone): a summary opened "7:00am · Café Example" with the Watch asleep until 7:29, and the first seven hours of each day's chat, commits, mail and notes were never read. The `DATE`/`DAY_NAME`/`MONTH_DAY` shell vars are just the date string and are unaffected. The `HH:MM` strings INSIDE the report (wake/sleep/stop/travel times) render in whatever timezone the user was physically in that day, via `resolve-day --tz <IANA>` (`lib/travel-timezone.js` auto-detects this from the `travel` timeline; defaults to the home zone, instance `tz`, when home or unrecognized). Non-location harvests (Step 2) still arrive in UTC/the home zone and must be converted to the SAME display tz before anchoring to a stop's prose, so a stop's H3 time and its aside's time agree. Added 2026-07-15 per the user, replying to a wrong-looking Jul 13 summary: "The daily summary should always be my local time." **Per-stop local time ("show the local time at each location when I was there"):** `DISPLAY_TZ` is now only the day's default. `resolve-day` stamps every stop with the zone at its own coordinates (`stop.tz`, `lib/geo-timezone.js` `timezoneForCoords`) and re-formats its `start`/`end` there; the day-level `tzs[]` lists the distinct zones. When the day crosses zones — `tzs` has more than one entry, OR its single entry differs from the day's `tz` (`crossesZones()`; e.g. a long-haul flight day defaults to the home zone because the user began it at home, yet every stop was at the destination) — wake and last activity are re-zoned to the stop the user was at, and every rendered time — stop headers, walk/leg lines, follow-up ranges, Tasks closed, unmatched calendar events, wake, last activity — carries a short zone label ("5:00pm CEST" … "4:22pm IDT"), and the manifest gives each stop its `tz_abbr`. Any time YOU state in prose on such a day (Step 2 harvested anchors included) must be converted to the zone of the stop it anchors to and carry the same label. This reverses the 2026-07-30 "the clock never jumps mid-narrative" display rule; the day WINDOW (midnight-to-midnight in the origin zone) is unchanged. Single-zone days render exactly as before, no labels.

## Step 1 — Compute target date + resolve the day

`daily-summary-run` always hands you an explicit date (the dispatch instruction at the end of this prompt) — use it. For the scheduled run it is "yesterday" in the user's CURRENT local timezone (`bin/local-day yesterday`), not yesterday in the home zone: this job fires at 04:00 local, and far east of home "yesterday" in the home zone at that moment is two local days ago (one Saturday-04:00 run rebuilt Thursday as a duplicate and Friday never shipped). Only if no date reached you at all, compute it the same way:


**`day-statements` first (2026-10-17).** It reads the day's chat with a model and writes `/tmp/day-statements-$DATE.json`: the places the user named with their activity and companions, labels, non-stops, "that's all the stops", and the kind of each iMessage the user sent that day (`self_messages`: correction / declarative / chatter, the source of `corrections[]` and `declarative_self_messages[]`). resolve-day, day-path and the review all read it; until 2026-10-17 nothing ran it, so every summary was built without the user's words (Friday Oct 16 lost the companions of the dinner the user named, "had dinner here <maps link> with Sam and Alex"). `daily-summary-build prep` also runs it when the file is absent, and resolves the day again when `/tmp/resolved-day-$DATE.json` is older than it, so a missed step here costs a re-resolve (give that `prep` call a 600000 Bash timeout), not the user's words; `confirm-venue` never runs it. ## Step 2 — The harvest is code: read `manifest.harvest` (2026-10-04)

These facts do not affect WHERE the user was — they hang off the stops by timestamp. **You no longer fetch them.** `daily-summary-build prep` harvests them and writes `manifest.harvest` (also `/tmp/ds-harvest-$DATE.json`) — `lib/daily-summary-harvest.js`, over the same window resolve-day uses (the zone the day was cut in; the raw-fact cache is keyed on that zone too, so a cache cut in another zone is refetched):

1. **Chat** — the day's `jori_messages`, both roles (`kind: "chat"`, `role`, `text` trimmed to 600 chars, `id`). The same rows the settle loop mined.
2. **Commits** in the jori repo (`kind: "commit"`, `sha`, `subject`) and **files added** that day (`harvest.new_files[]`). `prep` also lays the commits onto the day JSON as `commits[]` (local clock, the stop each belongs to or, before the first stop, its `pre` group; `autonomous`; `omitted` when routine) and into `manifest.commits[]` (the ones that will print), listed under their stops — see 4.2 `commits`. `harvest.prior_commit_tags` is the previous seven days' autonomous tags, which decide what is routine.
3. **Mail the user sent** from the user's own Gmail, not Jori's (`kind: "sent_mail"`, `subject`, `snippet`, `thread_id`) — `gog gmail search from:me … -from:<the agent's addresses>` (instance `owner_email`, `agentAddresses()`).
4. **Apple Notes** created or edited that day — titles and folders only, never bodies (`kind: "note"`).
5. **Messages — iMessage/SMS, WhatsApp and Slack, both directions, 1:1 and groups** (`kind: "message"`, `channel`, `chat`, `is_group`, `from_me`, `who`, `text` trimmed to 300 chars; 2026-10-27) — `lib/day-messages.js`. Code bounds volume by structure only: every 1:1 chat (up to 80 messages), up to 60 from a group the user wrote in that day (the user's own always kept), the last 12 of a group the user only read; reactions, protocol rows, statuses and newsletters dropped. `harvest.counts.message_sources` gives per-channel totals and `dropped`; a failed channel is `harvest.errors.messages_<channel>`. `who: "Jori (as me)"` is a WhatsApp message Jori sent from the user's number.

`harvest.counts` says how many of each, and **`harvest.errors[<source>]` is set when a source could not be read** — say "didn't capture" rather than treating a failed source as an empty day. Raw facts are cached per date, so a re-prep re-anchors to the renumbered stops for free; `prep --fresh-harvest` forces a refetch. If you genuinely need more than the 600 chars of a chat message, read that one row by `id` — don't re-harvest the day.

5. ~~Google Tasks completed~~ — **do NOT harvest this; `daily-summary-build prep` owns it (2026-08-23).** the user: *"the day's summary should include a list of tasks closed on this day … remembering when a task was done is extremely important for me."* A hand-harvested completion had nowhere deterministic to land — no skeleton section, nothing in the stored day JSON — so it survived only if you chose to mention it. `prep` now reads every Google Tasks list itself (`lib/daily-summary-tasks.js`), keeps what was closed inside the day's **local** window (the day's display tz, not always the home zone — a Paris day splits at Paris midnight), and writes `tasks_completed[]` onto the day JSON. `render` prints it as its own **"Tasks closed today"** section, `publish` stores it (so the log outlives a `gog tasks clear`, which permanently drops completed tasks from Google's own list), and `daily-summary-review` fails the report if a closed task is missing from the shipped HTML. It is in the manifest as `tasks_completed[]` for context only — see the prose rule in 4.2.
6. ~~Google Calendar events~~ — **do NOT harvest this; `resolve-day` owns it.** Since the 2026-08 fix in `lib/location-calendar-fuse.js`, calendar reads go through `gog` (a properly-scoped calendar grant), so the resolved day already carries every event: those overlapping a stop as `stops[].calendar_event`, the rest as `unmatched_calendar_events[]`. The old instruction to call the Calendar MCP existed only because the in-process fetch used a Gmail push token with no calendar scope and 403'd; that is no longer the path. Keep the "Every calendar event appears" rule intact — it is satisfied from those two fields.
**Do NOT** re-harvest `imsg sent` here — `day-statements` (run by `prep`) already has a model read and classify the day's sent iMessages, and `resolve-day` segregates that reading into `corrections[]` and `declarative_self_messages[]`. Adding another raw harvest would undo that trust partition.

**Do NOT** re-harvest location data (`findme history`, `location-stops`, `location-segment`, Supabase `location_history`) — `resolve-day` already owns that and guessing alongside it defeats the point.

## Step 3 — Facts are already anchored to stops

`manifest.harvest.facts_by_stop` maps each **settled** stop id (the ids your prose JSON keys by) to the facts whose timestamp falls inside its `[start_ts_ms, end_ts_ms]`; `facts_by_leg[]` (`{from, to, facts}`) holds facts in the travel gap between two consecutive stops; `orphan_facts[]` holds the rest (wake/sleep-adjacent activity, undated rows). This is arithmetic, done by code — read it, don't rebuild it. Every `at` is UTC ISO; convert to the stop's display zone before quoting a time (see the display-time rule above).

**`kind: "correction"` facts are the user telling you what happened (2026-10-11).** They come from `data/day-corrections/<date>.jsonl`, written with `bin/day-correction` by the email-inbound turn when the user replies to a summary by email (an email never reaches the chat harvest), and since 2026-10-22 by the fix loop and chat when the user corrects a past day (`channel: chat`): it is the corrected layer on top of the stored day that every reader sees first. Each carries the user's `text` verbatim, the `window` it is about, and sometimes a `reading` — the recording turn's own disambiguation (which activity goes where, what the map says), kept apart from the user's words; weigh it like any evidence, but where it and the user's words are both there, the user's words win; code anchored one copy to every stop the window touches, so the same sentence can appear under several stops. Vet any name in it geographically first (Step 3c — it binds to a stop only if that business is within ~60 m of it). State what it establishes on the stop it belongs to, in the user's terms ("coffee with Sam, and the bagels for the neighbours came from the bakery"), as fact — the user said it. Do not invent a time, a place or a stop the user's words don't give, and don't repeat one correction as a full sentence under every stop it was copied to: put it where it fits (a "coffee stop" belongs on the café, not the door either side of it). A correction never creates a stop; if the day JSON has no stop it fits, that is a defect in `resolve-day`, not licence to add one.

**Step 3a — (superseded by Steps 3c–3d below.)** The old "transcript-overlay" — manually scanning chat for answers to location-enrich questions and hand-patching `place.name` — is now done programmatically: `daily-summary-build prep` mines the day's chat — both the answers to Jori's own location-enrich asks (`manifest.ask_answers[]`, applied automatically) and volunteered venue statements (`manifest.chat_venue_candidates[]`, advisory) — and settles every title in the day JSON. You no longer hand-edit `place.name`; you VET what `needs_review` flags (3c), write the confirmed map (3d), and re-settle. Keeping this note so the old instinct ("patch the name in place") is explicitly retired.

**Step 3b — Photos are embedded, NEVER interpreted (2026-07-16, the user's explicit instruction).** Do NOT open, view, fetch, read, or OCR any stop's photos. The builder already embeds every stop's photos into the email skeleton as image URLs (`renderStopPhotos` → `photos embed-uuids`), so they render in the summary as-is — that is the ONLY thing that happens with photos, and it needs nothing from you. **Never load photo image data into this session.** Doing so gobbled the context budget (a photo-heavy France travel day pushed the session 185k→241k and rotated out before Step 5 could persist — the 2026-07-15/16 daily-summary failures). Venue identification relies on the chat + resolver + transaction signals only (Steps 3c–3d). A stop with no chat/txn confirmation stays hedged at its resolver tier, and its photos still appear in the email regardless. Under-naming a venue is completely fine; never load a photo to try to name it.

**Step 3c — Vet the chat venue candidates, then sweep the day's chat for the answers the regex can't see.** `manifest.chat_venue_candidates[]` are ADVISORY — regex mined them from chat, so some are false (the 2026-06-27 run mis-mined "the villa is 1.6" = a property's *value*, and "the balaboosta restaurant is a great rec" = a tip the user *didn't visit*, both onto random stops). For each candidate use judgment: is it the user saying *where the user actually was* ("we went to Ping's"), or property/value talk, a recommendation the user is commenting on, or something else? Bind a real one to the GEOGRAPHICALLY-correct stop (cross-check the candidate's `stop_id` hint against the stops' coordinates — the regex binds by time and can be a stop off). **For a named business that cross-check is a lookup, not an eyeball (2026-10-11):** run `places_nearby "<name>"` with `lean: true` (names and positions only — the cheap tier) at the stop's own `lat`/`lon` and bind the name only if that business sits within ~60 m of the stop. A different business at the stop (or none) means the name belongs to a separate errand, not to this stop: on 2026-10-10 "a coffee stop and a bagel run at the bakery" was bound to a café stop whose GPS rest and coffee photos sat 13 m from another café while the bakery is ~140 m away, so the summary said "coffee with Sam at the bakery", which was false. The same applies to a name inside a `correction` fact. When one sentence joins two activities under a single "at" and the geometry separates them, put each where the geometry puts it, and say only what the stop supports ("coffee with Sam") rather than naming a venue the stop doesn't contain. Carry the `sentiment` ("disappointing") into that stop's prose.

**The miner only matches VENUE grammar ("we went to X", "X was disappointing"), so it misses the two shapes that matter most for a hedged stop:** an answer to one of the day's own location-enrich asks (Jori's ask names the time — *"9m near Plage des Minimes around 12:49 …"* — and the user's reply may land hours later, with unrelated messages in between), and an answer that names an AREA or an ACTIVITY rather than a venue (*"we were walking along the coastline in the minimes park"*, *"we were at the beach all afternoon"*). Both are confirmations. **So: for every stop still at `GUESS`/`WEAK_GUESS`, scan the day's chat for anything the user said about that time window before you write its prose.** What you find goes in the confirmed map in 3d exactly like a vetted venue — the label may be an activity or an area, and that is fine; the user's words beat a POI guess every time. (A window already marked `provenance.non_stop` needs nothing from you — `findme` and `resolve-day` handled it.)

**Step 3d — Write the confirmed map + re-settle + write back.** Collect every venue you CONFIRMED in 3c into `/tmp/ds-confirmed-$DATE.json` as `{ "<stop_id>": "<venue name>" }`. This map also OVERRIDES a mis-bound `ask_answers[]` entry — your vetted value always wins over a mined one. Then:
```bash
# 1. Re-settle with the confirmations -> those stops become `title_certainty: "answered"`.
#    Cheap and idempotent — settle as many times as it takes to get the JSON right.
~/Dev/jori/bin/daily-summary-build prep $DATE --confirmed /tmp/ds-confirmed-$DATE.json
# 2. Persist each to the PERMANENT record so weekly/monthly + future recall self-correct.
#    (the summary is a confirmed-fact write path.)
~/Dev/jori/bin/daily-summary-build confirm-venue $DATE <stop_id> "<venue>" --source chat
```
Run `confirm-venue` once per confirmed stop. It patches the matching `location_history` visit row (`place_name` + `place_type=user-confirmed`) within the stop's window+300m, so the next resolve-day run picks it up at user-confirmed weight. Idempotent. If a stop stays WEAK_GUESS after this (no chat/txn nailed it), leave it hedged and let Step 5's question prompt ask about it.

**One exception to the write-back:** when what the user said is that it *wasn't* a stop ("just walking through"), put the label in the confirmed map for today's render but do NOT run `confirm-venue` for it — that would stamp the row `user-confirmed`, i.e. a real venue by this name. `findme resolve` already owns that row (`place_type='non-stop'`, the user's words in `place_name`); leave it alone.

**Step 3e — Who was there: settle it from the user's calendar and the user's words before the review asks (2026-10-21).** One evening the user's calendar had "Sam and Alex" at 8pm, the dinner stop began at 8:06pm, and at 10:20pm the user wrote *"We had a light dinner at the bistro"*; the summary named only the user's partner, the review flagged it, and the fix loop asked the user at 4:37am. A check the calendar plus chat can answer is resolved without asking. So, before Step 4: for each stop with a `calendar_event`, and each `unmatched_calendar_events[]` entry that begins within 30 minutes of a stop (an event with no location lands there), read whether its title names the people the user was meeting (your reading, Rule #0b, never a pattern). A call or video meeting is not company at a stop (a link and no street address, or a title like "Call with Alex" by your reading; the day's calls are code's own line, § Calls), so leave those out. Where it does name people, and nothing contradicts it (the user's chat that day doesn't say it was cancelled, moved, or that they didn't come; the event isn't declined or cancelled; no other stop, and no photo location `resolve-day` attached to another stop, puts the user elsewhere at that time; never open a photo for this, Step 3b), they were with the user at that stop. Record each name Jori already knows:
```bash
~/Dev/jori/bin/location-annotate --start <stop start, ISO with offset> --end <stop end> --companion <name> [--companion <name>]
```
then, only if you recorded someone, resolve the day again so the stop carries them (`prep` reuses the resolved day on disk, which predates them): Step 1's `resolve-day --tz "$DISPLAY_TZ" "$DATE" > /tmp/resolved-day-$DATE.json`, then `daily-summary-build prep $DATE`, with the 3d confirmed map if there is one. Its venues are already on the user's records (3d wrote them back); check that its stop ids still point at the same stops before reusing it. `location-annotate` refuses a name Jori has never seen (exit 4, nothing written): a new person goes on the user's records only on the user's own word, so never pass the calendar title as `--new-companion-authorized`; leave it, and the review and fix loop ask the user. This settles **who**, never **where**: the calendar still neither makes a stop nor names a place by itself (the rule above), and an event that could belong to two stops, or that the user's words contradict, is left alone.

**Travel modes are not yours to infer.** The spine (`manifest.spine[]` legs, settled by `settleLegModes` in `lib/daily-summary-render.js` against `manifest.mobility[]` taps) is the single authority on how the user got between stops; `routes[]` speaks only where the spine has no leg. Use the leg's `mode`; when it is `riding` + `mode_uncertain`, say "rode" / "traveled" or name one of its `mode_candidates` only if the user's own words or a tap settle it. (A distance/duration mode table used to live here and disagreed with the spine — retired 2026-10-04.)

## Step 4 — Render via the deterministic spine builder

**The location spine is built by CODE, not by hand.** The report agent repeatedly merged distinct stops and silently dropped photos (2026-06-20: a kebab lunch lumped into the beach-neighborhood block; the recurring 0-`<img>` failure). Per the user's directive — *determine steps programmatically, enrich with calendar, only THEN produce the report* — `bin/daily-summary-build` owns the spine (H1, wake/sleep, every stop `<h3>` header, per-stop photos, travel legs, the "Events not matched" + "Corrections & follow-ups" lists). **You write ONLY prose into named slots — you cannot rename, merge, relocate, or drop a stop or its photos.**

**And the spine is settled as JSON before any of it is formatted (2026-07-27).** `prep` decides identities; `render` prints them. Everything you can change about a title, you change in the JSON and re-settle — never by writing prose that disagrees with what the header will say.

### 4.1 — Settle the day's JSON (repeat until it's right), THEN format

**Two separate commands, in this order, and never collapsed back into one (*"the day skeleton building should be deterministic (json). it may require multiple passes to get the json right. once it's as good as we can get it, we should format the final email."*).**

```bash
# A. Settle the facts. No HTML, no photos — cheap, re-runnable.
~/Dev/jori/bin/daily-summary-build prep $DATE
#    ... vet what it flags (Steps 3c-3d), then settle again with your answers:
~/Dev/jori/bin/daily-summary-build prep $DATE --confirmed /tmp/ds-confirmed-$DATE.json
# B. Only once the JSON is as right as you can get it — format the email.
~/Dev/jori/bin/daily-summary-build render $DATE
```

**`prep` settles, it doesn't render.** It reads `/tmp/resolved-day-$DATE.json` (Step 1) and runs the **settle loop** (`lib/daily-summary-day.js`): answers to the day's own location-enrich asks, chat-venue mining, in-person/mobility transaction matching, provenance tiering — **repeated until no stop's title changes** (cap 5 passes), because resolutions cascade (settling one stop changes which stop a later chat line binds to). It writes the canonical `/tmp/ds-day-$DATE.json` plus the **manifest** (`/tmp/ds-manifest-$DATE.json`, also printed): per-stop `{id, start, end, title, title_certainty, title_kind, needs_review, place_name, place_source, provenance:{tier,hedge,non_stop,confirmed_name,alternatives,sentiment,signals}, duration_min, possible_unlogged_excursion, companions, calendar_event, photo_count, transactions}` plus `standout_transactions`, `mobility`, `chat_venue_candidates`, `ask_answers`, `settle_passes`, `unmatched_calendar_events`, `calls` + `calls_left_out` (the day's calls, see § Calls), `unknown_stops`, `corrections`, `tasks_completed` (+ `tasks_completed_error`).

**The spine is the frame (2026-09-07).** `manifest.spine[]` is the day as one ordered sequence — `dwell → leg → dwell → …` — built by `bin/day-path` from the GPS fixes reconciled against the visit rows. Write the narrative *along* it: every dwell is a stop in order, every leg is what happened between two stops, and a leg carries its own `miles`, `streets`, `mode` and `holes`, so a travel sentence never guesses from a whole-day blob. Language follows the node: assert a dwell whose `tier` is `user-confirmed`/`corroborated`; describe a `stay-point` by where it is ("stopped 20 minutes near 8th & 34th"), never with an invented venue; do not assert a duration for a dwell whose `witnessed_min` is a sliver of `mins` — say when the user arrived, not how long the user sat. A leg's `confidence` says how much the phone saw: `partly inferred` legs carry `holes` (don't narrate the routed guess, and don't narrate the holes either: no "the phone lost the user between 35th and 14th", see the GPS-silence rule in 4.2); `mode` is what the pace says (`walking` / `riding` / `driving`), and a `riding` leg the pace could not name carries `mode_candidates` (`subway` / `bus` / `cab`, the day's taps first) and `mode_evidence` (the mobility charges on the day, e.g. `MTA $3`). When the day has exactly one such leg and one kind of tap, the builder settles it for you — `mode: "subway"`, `mode_uncertain: false` — and you may say "took the subway". Otherwise pick from `mode_candidates` only if the user's own words settle it, else keep it mode-neutral ("13 minutes back to the flat"). **Never "biked" / "cycled"** unless `mode` is `bike` (a Citi Bike or other micromobility charge) or the user's own words say so — a 13-minute ride at 11–15 km/h between two fixes is the subway as readily as a bike (2026-09-08). `his_words[]` on any node are the user's statements about that stop or stretch, already bound by the model that read them. `records_set_aside[]` are visit rows the trace never supported (a `departed_at` written a day late; a geocode of somewhere the user only passed): not on the map, not in the spine — **never narrate them**.

**`title` is the contract.** It is the exact string the header will print — settled once, in the JSON, by code. `title_certainty` is `answered` (the user told us) | `known` (home/known-recurring) | `corroborated` (a card charge agrees) | `guess` | `weak_guess` | `none`, and `title_kind` is `venue` | `area` | `movement` | `unknown`. **Write prose that agrees with the title.** If you can't, the title is wrong — fix the JSON and settle again; don't write around it.

**Read `ask_answers`, `multi_answer_replies` and `unattributed_replies` before you trust a title — these are the user's own words about the day.** They exist because on 2026-07-27 the user said *"some of my answers were lost"*, and the user was right.

- **`ask_answers[]`** — answers mined from chat and bound to one stop, with `method` (`thread` = the user used the app's Reply action, exact; `overlap` = the user named something only that ask mentions) and `applied` (whether it settled the title). `applied: false` means it IS an answer but not a printable title — a sentence like *"We stopped at one of the restaurants and had a plate of cheeses and wine"*, or a `kind: "rejection"` (a bare "no" to a *"was it X?"* ask, which rejects the venue, **not** the stop). Turn those into a title yourself. **A stop whose resolver place is `user_confirmed` is never retitled by a mined answer (2026-10-11):** the `user-confirmed` visit row is the later authority (`findme resolve` wrote it from that reply, or from a correction the user made after it), so an earlier "Just passing through" cannot undo "that was where I met a friend on the dog's walk". If a stop's row and the user's latest words disagree, fix the row (`findme resolve <visit_id> "<name>"`, every twin row of the window) and re-prep; do not paper over it in prose.
- **`multi_answer_replies[]`** — **the one you must not skip.** One reply that answers SEVERAL asks, which is what a catch-up reply looks like after a stretch offline. The real one: *"No. We saw the last panache first, then the vikings, then the colliseum show. We had lunch after the last panache at the rotissirie (roast chicken and potatoes). Just walked around in between."* — four answers, four stops, one message. Nothing is auto-applied from these, deliberately: the pieces cannot be attributed deterministically (*"We had lunch after the last panache at the rotissirie"* shares its rare words with the **show** ask, not the lunch ask it answers), and a wrong guess would invent a fact. Each entry carries `segments[]`, `threaded_to`, and every `candidates[]` ask with its `stop_id`. **Read it, decide which part answers which stop, and write all of them into the confirmed map.** Every stop it touches is flagged `needs_review` until you do.
- **`unattributed_replies[]`** — things the user said while a location ask was open that couldn't be bound to one. Usually not about location; occasionally the answer, phrased in words the ask didn't use. Skim them; a lost answer is exactly what this list exists to stop.

A mis-bound answer is the one failure mode this machinery can produce on its own — if an entry looks bound to the wrong stop, override it in `/tmp/ds-confirmed-$DATE.json` and re-settle. `settle_passes[]` shows what each pass changed, so a title that only appeared on pass 3 can be traced to the cascade that set it.

**The chat window covers the target day AND the next one**, because an ask about an evening stop is routinely answered the following morning. Binding is per-ask with a 12h window, so the extra day can't contaminate anything — but it does mean a re-render tomorrow can pick up an answer today's run never saw.

**`needs_review` is your work-list, and its `reason` is ranked.** Two reasons mean *the answer already exists, go read it* — `"the user answered this in a reply covering several stops"` and `"the user rejected the venue we guessed"`. Do those first; they're free. The rest (`thin guess with competing alternatives`, `single-signal venue guess`, `no label at all`) are genuine unknowns. A stop with `title_certainty: "answered"` and no `needs_review` needs nothing from you.

**`render` formats and decides nothing.** It reads the settled `/tmp/ds-day-$DATE.json`, embeds each stop's photos (favorite > earliest, ≤3, videos as poster-frames; each photo it could not show is recorded on the manifest stop as `photos_not_shown` with the reason, since 2026-10-17), and writes `/tmp/ds-skeleton-$DATE.html` with every `<img>`, header, travel leg and bottom list in place, plus `{{PROSE:<id>}}` / `{{ASIDE:<id>}}` / `{{OTHER_ANCHORS}}` slots. Photo embedding lives here, not in `prep`, because it's the expensive step and there's no reason to pay it on every settle pass. (Photos are never *read* — see Step 3b.)

**Standout purchases (bank data — handled deterministically by the builder).** `daily-summary-build prep` also fetches the day's `plaid_transactions` locally (service-role REST, read-only) and runs `selectStandouts` (`lib/daily-summary-transactions.js`) to pick only the day's **standout** spends — large, experiential (dining/entertainment/travel/shopping/personal-care), or in-person purchases tied to a visited stop — never the full ledger. Each is surfaced two ways for you to weave in: `stops[i].transactions[]` (matched to that stop by merchant↔place name; an in-store charge whose spelling no stop shares, one spelling for the user's other spelling, is linked by a model reading since 2026-10-24, `lib/standout-stop-link.js`) and the day-level `standout_transactions[]` (all of them; unmatched ones carry `stop_id: null`). Every entry has `{merchant, amount_usd, category, payment_channel, pending, stop_id}` where `amount_usd` is the **code-computed** string (e.g. `"$120"`, `"$66"`). **BANK-DATA POLICY (rule 5 carve-out):** these rows are jori-model-only — reason over them in this turn, render them ONLY into this self-addressed email, and NEVER pass an amount/merchant into a claude.ai connector call (Gmail/Calendar/Slack search). See `agent/CLAUDE.md` § Financial Operations rule 5.

### Calls — code's line in the timeline, not a stop

The day's calls are in the summary, as code's own lines. `prep` settles them into `day.calls` through the installation's hook (`lib/_ext/day-calls.mjs`, loaded by `daily-summary-build`; without it a day has no calls, and the installation's companion to this playbook describes its own calls and their sources). `render` prints each as a bullet at its time, set like the work lines under a stop (bold time, then plain text), with what was discussed as very short one-line sub-bullets: **11:00pm-11:30pm** `Call with <who> · 30 min · calendar times`. A call in a stop joins that stop's work list in time order; a call outside any stop gets a one-item list of its own. `manifest.calls[]` carries each `{who, local_time, minutes, status, source, line, talk, talk_points}`; `status: "scheduled"` means nothing read whether it took place, so it is worded as on the calendar, never said to have happened; `calls_left_out[]` are calendar slots code settled did not happen. A call's event leaves "Events not matched". A call is never a stop, a visit, a map point or part of the stop count, and no prose slot renames or drops it.

```json
  "wake_caveat": "", "sleep_caveat": ""

```

**`commits` (2026-10-21) — what the user worked on, in plain language, under the stop where the user did it.** the user: *"commits should be included in plain language in the daily summary ... based on the time of day"*, then *"don't put it in a separate section. list it under each stop where relevant (I'm not working on things when walking)"*. ## Step 4.5 — Consistency: the structural checks are code, the tier check is yours

The deterministic builder (Step 4.1–4.3) guarantees photo parity, header/time fidelity, and stop integrity **by construction** — those drift modes (the 2026-04-18 NYBG zero-`<img>` day, the kebab-lunch merge) are structurally impossible. **Checks 1–3 below run inside `daily-summary-review` (Step 4.6) since 2026-10-04** — do not grep for them yourself; fix what its findings name:

1. **No unfilled slots** (`kind: "unfilled"`). A prose slot id was wrong — fix `/tmp/ds-prose-$DATE.json` and re-run `assemble`.
2. **No photo-count phrasing** (`kind: "quality"`, "photo-count phrasing"). Strip the count from the prose JSON and re-`assemble`.
3. **Every standout purchase is accounted for, none invented.** A `missing` finding names a `standout_transactions[].amount_usd` absent from the HTML — weave it into its stop's prose (or one `other_anchors` line) and re-`assemble`. An `invented` finding lists dollar figures the builder never computed — remove them; you never introduce an amount.

   **A standout with no `stop_id` carries no meal or time-of-day either (added 2026-09-13).** Plaid gives no reliable intraday timestamp (`authorized_datetime` is frequently a midnight-UTC placeholder, not a real time), and `payment_channel: "online"` charges are never geo/time-bound to a stop by the matcher — so when `standout_transactions[]` hands you an entry with `stop_id: null`, you have exactly the merchant, the amount, and the date, nothing else. Weave it into `other_anchors` neutrally ("A Bubaburek order came through, ~$61.76") rather than staging it inside a specific stop's prose with an invented time-of-day or meal ("settled in for the night with dinner delivered from Bubaburek") — that stages a fact the manifest doesn't support. Root-caused 2026-09-13: an unattached Bubaburek/DoorDash charge got narrated as that evening's dinner; it was actually a morning order for two family members' lunch. 4. **Tier-language match (the 2026-06-27 guard) — and it runs BOTH ways (2026-07-27).** The check below catches prose that over-asserts a hedged header. The opposite failure ships just as often and is what the user flagged on 2026-07-26: a header hedging `~L'Équinoxe? · unconfirmed` above prose that says plainly where the user was. Re-read every hedged stop's prose: **if your own sentence names the place or the activity, you knew — go back to 3c-3d, put it in the confirmed map, re-prep, re-assemble.** A hedged title above a body that answers it is never acceptable, in either direction. Re-read each hedged stop's prose against its H3 — if the header says `~X? · unconfirmed` but the prose says "you went to X, the famous Y", rewrite the prose to hedge and re-`assemble`. A venue you genuinely confirmed in 3b–3d should already read `title_certainty: "answered"` (bold H3) after the `--confirmed` re-settle; if it's still hedged, you didn't write it into `/tmp/ds-confirmed-$DATE.json` — fix that, re-settle, `render`, re-assemble.

## Manual recovery — backfill a missing day
