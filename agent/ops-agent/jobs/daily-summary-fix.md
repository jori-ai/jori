DAILY SUMMARY FIX — the fix loop for a daily summary the reviewer did not confirm. Runs as an ephemeral Opus agent (launchd `ai.claude.daily-summary-fix`, `trigger-daily-summary-fix.sh`), one date per run. Your job: find the root cause of every issue the reviewer found, fix it (wording, the user's records, or the code), rebuild the day, and have the reviewer read it again. Repeat until it confirms the day is correct and accurate, then send it. When a fix needs the user, ask the user in chat; you will be started again when the user answers. **The email waits for the user's answers**: every question goes out before the summary does, and `daily-summary-fix gate` (code) decides when it may be sent.

**Why:** *"catching issues is the primary job [of the reviewer]. if issues are found, a second process should find the root cause, fix it, and regenerate as needed until the reviewer confirms the day summary is correct and accurate. If a fix isn't possible without consulting me, ask for guidance in the chat, and then continue the process."* Also: *"the daily summary email should include a section at the end about any issues found by the reviewer and how they were fixed."* Before this, the reviewer's code-level findings went nowhere: one day shipped the rented flat as four stops, the dinner the user named (with two friends) under "Day's other anchors", and a 3-hour café stop over it, though the reviewer had flagged most of it.

**Why the gate:** *"Good guesses - but these questions should come before the summary is sent, not after."* Monday Oct 19: this fixer asked its three questions at 04:42 the user's time and sent the email at 04:55; the user answered at 07:56. It did what this file then said: the stop rules sent a never-sent day as soon as nothing was left to fix without the user, and the deadline said to send the best version whenever the day was waiting on the user's answer, because nothing in code would send it at a deadline. Now the first question opens the day's answer window, `gate` holds the email until every question is answered or the window closes, and the hourly sweep starts you when it closes.

**Why the quiet hours:** *"Why wait until 4:37am to ask this?"* and *"Create an improvement to ask in time."* The day is built in the user's small hours, so its questions were sent then: eight more reached the user between 4 and 5am Jerusalem time from Oct 22 to Oct 27. Now `daily-summary-fix ask` holds a question composed inside the user's quiet hours (`agent/local/config/daily-summary-fix.json`, read in the user's current timezone). From `awake_from` on, the user counts as up when the user's phone says so (the sleep-night reading hum's quiet hours use) or, without a phone reading, when the user has written in chat; at the latest when the hours end. The hourly sweep (cron) only marks the day due: from cron the outbound check cannot reach the Max sign-in, so a question sent there would skip its check. The launchd runner (`trigger-daily-summary-fix.sh`) sends it with `daily-summary-fix release-held` after its own Max sign-in check. Code does the timing; you ask exactly as before.

**Read before you start:** `jobs/daily-summary.md` (Steps 1–5: how the day is built, settled, written, assembled, published and sent; you re-run those steps, you do not reinvent them) and `~/.claude/skills/location-spine/SKILL.md` (for any wrong, missing, split or misnamed stop: find the rung where two stores disagree before changing anything).

## Helpers: Sonnet at low effort reads and sorts, you (Opus) decide and fix

**Why (the user, 2026-10-22, D5):** lower this loop's cost with lower-effort helper agents and Sonnet for triage, keeping Opus for the actual fix, on the same schedule. It cost $226 in its first six days (about $40 a day). A typical run is 150-200 turns on Opus at xhigh, and most of the bill is the context re-read on every turn (Oct 22 02:09: $25.50, 66M cache-read tokens, 177 turns): every photo list, message dump and code search you read yourself is paid for again on each later turn. A helper reads it once and hands you the few lines that matter.

**Spawn these with the `Agent` tool, `model: "sonnet"`, `effort: "low"`** (this playbook is the explicit instruction to set both; `trigger-daily-summary-fix.sh` also makes Sonnet the default for any helper). Each prompt says: read-only, no writes of any kind, answer in at most ~40 lines (JSON where asked), quote ids/timestamps/file:line rather than paraphrase.
1. **Round-start triage**, once per round after the review: give it `/tmp/ds-review-<date>.json`, the state file and the manifest/day/prose paths; ask for each high/medium finding `{n, headline, layer: prose|records|code|ask, evidence: [≤3 short lines with ids or file:line], his_words: [verbatim quotes that bear on it], photos_in_window: [taken_at, venue reading, detected text]}`. The layer is its guess; you decide, and re-read anything you act on.
2. **Evidence before a question** (step 4's "first make sure no source already says"): the user's photos in the window, the user's messages, email and calendar around it, `companion-presence who …`. It returns what it found, with ids.
3. **Reading the user's answers** (a run started by the user's reply): the user's messages since the open questions, verbatim with timestamps, and which question each seems to address. Which questions they settle (`daily-summary-fix answered`) stays your reading.
4. **Finding code** before a code fix: where in `resolve-day.js` / `daily-summary-*.js` / `day-path` a stop is dropped, merged or named. It returns file:line excerpts; you read the lines you will change.
5. **The unrecorded-send check** (Failure modes): search the user's inbox for the day's subject from the agent's own address (instance `agent_email`).

**Stays with you, on Opus:** the root cause, every record or code change, every `daily-summary-fix ask|answered|log|gate|mark-sent|done`, `day-correction`, `findme resolve`, `location-confirm`, `self-improve-auto-apply`, publish and send. The **critic** (code fixes) stays on Opus at lower effort: spawn it with `model: "opus"`, `effort: "medium"` (it is the safety gate on landing code, so not Sonnet). Never delegate a write, and never send on a helper's say-so.

Runs that used helpers show `claude-sonnet-5-5` next to Opus in `models` of their row in `agent/logs/ephemeral-forks/job-costs.ndjson`; compare `total_cost_usd` and `cache_read_tokens` per run against the Oct 17-22 baseline ($1.29-$59.80, median about $12).

## Inputs

- The task line carries the state file for the date: `data/daily-summary-fix/<date>.json` (`status`, `requests[]` with reasons, `answers[]` from the user, `questions[]` already asked (each with its number `n` and, once settled, `answered_at`; one composed in the user's quiet hours also has `held_until`, then `sent_at` when it was asked, or `dropped_at` + `dropped_why` if it stopped mattering first; `release_due_at` / `release_error` on the day say it is due to be asked or the last send failed), `hold` / `correction_hold` (the answer window: `until`, and `label` as the user reads it), `log[]` of what was done, `sends[]`). Re-read it with `daily-summary-fix status <date>` before you decide anything: the snapshot in your task line can be older than an answer that came in since.
- **A day can arrive with nothing for the review to fix**: the daily-summary run itself asks its questions before sending (`daily-summary.md` Step 4.7) and leaves a confirmed day held. Then the work is the user's answers: apply them, rebuild, review, and Send.
- `/tmp/ds-review-<date>.json`: the latest review (`confirmed`, `findings[]` with `kind`, `severity`, `headline`, `detail`, `fix`, `fix_by`, slot).
- `/tmp/ds-manifest-<date>.json`, `/tmp/ds-day-<date>.json`, `/tmp/ds-prose-<date>.json`, `/tmp/daily-summary-<date>.html`, `/tmp/resolved-day-<date>.json`. If `/tmp` was cleared (a restart), rebuild them with Step 1 of `daily-summary.md` (`daily-summary-build prep <date>`) before anything else.
- **The user's photos** for the day: the `photos` table (`taken_at`, `latitude`/`longitude`, `device_venue` = the phone's own venue reading with nearby places, `detected_text` = signs in frame, `labels`, `persons`, `self_captured`). The review's FACTS list them per stop. A photo the user took at a place is evidence the user was there, second only to the user's words (*"the cafe antilia in the morning would be confirmed because i provided a photo - same for the milk bakery"*). **Check the user's photos before asking the user anything**: if a photo inside the window sits at the venue (the phone's venue reading or a sign names it, within ~50 m), that answers it; name the stop from it and say so in the log. A resolver or spine that ignored such a photo is a code finding.
- The user's messages for the day are in the manifest's `harvest` (the review's FACTS list them). Answers the user gave after a fixer question are in the state's `answers[]`; also read the user's chat messages since the question was asked (`jori_messages`, role `user`), since the user may have answered without the chat agent passing it on.

## The loop (at most 4 rounds per run)

**Round start: review.** If the latest review is older than your last change, run it again:
```bash
~/Dev/jori/bin/daily-summary-review <date> --repair     # Bash timeout 600000
```
`confirmed: true` → go to **Send**. Otherwise work every `high` and `medium` finding below. Ignore `low`.

**For each finding, find the root cause first.** Ask what made the report wrong, not just how to change the sentence. Then fix it at the right layer, and record it in plain words (this becomes the email's closing section, so write `--finding` and `--action` for the user: no stop ids, no tiers, no jargon):
```bash
~/Dev/jori/bin/daily-summary-fix log <date> --finding "<what was wrong, one plain sentence>" \
  --action "<what you did about it>" --outcome fixed|data-corrected|code-landed|asked|unresolved [--commit <sha>]
```

1. **Wording only** (`fix_by: prose`, and the facts are right): the `--repair` pass usually handles it. If it survived, edit `/tmp/ds-prose-<date>.json` yourself under the rules of `daily-summary.md` Step 4.2 (voice, at most two sentences a stop, no photo counts, nothing about GPS), then `daily-summary-build assemble <date>`. Outcome `fixed`.
2. **The user's records are wrong** (a stop named or timed wrong, a place the user named that has no stop, a stay split across rows, a missing companion on a row): correct the record **only with what the user's own words or the movement evidence prove**, and only through the sanctioned tools: `findme resolve <visit_id> "<the user's words>"` (the user's name for a visit; it refuses overlaps with exit 2: read why, do not force), `location-confirm save` / `save-visit`, `daily-summary-build confirm-venue <date> ...` (Step 3c–3d of `daily-summary.md`). Never PATCH `location_history` by hand and never invent a name the user did not give. Outcome `data-corrected`.
3. **The code is wrong** (the resolver merged a dinner into a café, a lodging stay split into four, a duplicate task line, a check missing in the review, a statement extraction that never ran): find the defect in the code (`lib/resolve-day.js`, `bin/day-path`, `lib/daily-summary-*.js`, `bin/daily-summary-build`, `bin/day-statements`, `lib/daily-summary-review.js`), write the smallest correct fix plus a test in `tests/`, run the related tests, then land it **only** through:
   ```bash
   ~/Dev/jori/bin/self-improve-auto-apply --summary "<plain one line>" --problem "..." --impact "..." --fix "..." \
     --side-effects "..." --files-json /tmp/dsfix-<date>-<n>.json --risk low|moderate --category bug-fix --critic SAFE \
     --base-rev "$BASE_REV" --details "<tests run; the finding it fixes>" --source dsfix-<date>
   ```
   `BASE_REV` is `git -C ~/Dev/jori rev-parse HEAD`, taken right before you read the files this fix changes. Build `/tmp/dsfix-<date>-<n>.json` from the files you changed with `~/Dev/jori/bin/self-improve-bundle --out /tmp/dsfix-<date>-<n>.json --base-rev "$BASE_REV" <each file>`, then restore those files in the working tree (the CLI writes them); never assemble the bundle with a hand-written command (on 2026-10-25 one wrote it over the changelog). Exit 7 means one of them changed since (another fix landed): re-read it, rewrite your fix against the current content once, and resubmit with a fresh `BASE_REV` and `--redo`; a second 7 → `unresolved` ("another change landed on the same code; retrying tomorrow").
   Get the critic verdict first: spawn an `Agent` (`model: "opus"`, `effort: "medium"`, see § Helpers) with the diff using the critic contract in `self-improvement-executor.md` § Critic subagent; anything but `SAFE` means revert and treat the finding as unresolved. Exit 0 → outcome `code-landed` with the commit. Exit 3 (high blast radius) → file it with `self-improve-request` (a Face-ID card) and log `unresolved` ("waiting on your approval in Improvements"). Exit 4/5/6 → `unresolved` with the reason. Never commit directly, never edit a file the landing tool refuses, never touch the fix loop's own files (`bin/daily-summary-fix`, this playbook, `trigger-daily-summary-fix.sh`) or the review's rubric to make a finding go away.
4. **Only the user knows** (two places fit and neither the user's words nor the user's photos decide it; who was with the user; whether a stop happened at all). First make sure no source already says: the user's messages, the user's photos, the user's email and calendar, and for who was with the user `~/Dev/jori/bin/companion-presence who <date> <from> <to>` (the family's phones against the user's GPS; wiki `feedback_day_review_check_channels`). Then ask one short, concrete question, offering the most likely answer so the user can just say yes:
   ```bash
   ~/Dev/jori/bin/daily-summary-fix ask <date> --question "Was Sam with you at Alex's in the afternoon, or just Alex?"
   ```
   It sends the question to chat, records it, logs it for the email's closing section and sets the day `awaiting_<owner_id>` (at most 5 questions a day; past that, the rest stay in the email's follow-ups). Exit 5 means the outbound check held the question back: it was not asked and holds nothing, so carry on without it. **Inside the user's quiet hours it does not send**: it prints `held (question n): …`, exits 0 and records the question with `held_until`; it is asked once the user is up (never by you, and never from the cron sweep), and the email waits for it exactly as for a question the user has seen; `gate` lists it under `held_not_asked`, not `open`. Treat it as asked: never re-ask it, never send it some other way, and never send the email early because it has not reached the user yet. **A question never cites a card charge, an amount or a health reading** (the questions pass the outbound check's model, which bank and health data must never reach; Oct 19's "there's a Karta parking charge" did): say "your 1:36 photo is a car park", not what the user paid. **Do not also `log --outcome asked`**: on Oct 19 the same two questions appeared twice in the closing section and pushed two open items past its 15-line cap.

   **Ask every question the day has in the same round, before you rebuild and before anything is sent**: the findings only the user can settle; every unknown stop the email would otherwise ask about in its follow-ups (the daily-summary run's own phrasing is in `/tmp/ds-prose-<date>.json` `questions`); who was with the user, where the phones and photos don't settle it; and any photo of the user's that contradicts a stop's title. Questions asked together buzz the user's phone once. The first question of the day tells the user the summary is waiting and until when (code adds it); a question asked after the first send says it only came up afterwards. Then keep working every other finding, rebuild and review once more, and go to **Send**: its gate holds the email while the user can still answer.

**Rebuild.** After any data or code fix: `daily-summary-build prep <date>` (re-resolves the day with the new records and code), then settle → write prose for the stops that changed → `assemble`, as in `daily-summary.md` Steps 4.1–4.3, then start the next round with the review. A wording-only fix needs only `assemble`.

**Stop rules.** A finding that survives two fix attempts is `unresolved`: log it and move on. After 4 rounds without confirmation, or when nothing is left that you can fix without the user, go to **Send**; its gate decides whether the email goes now or waits for the user's answers. A day that has been sent gets a correction only under the rules below; otherwise stop. When you give up on the remaining issues for good (nothing more you or the user can do): `daily-summary-fix done <date> --status gave_up --still-open <i,j,...|none>`. It files to the system channel, for system-issue-review, only the log entries you list (0-based indices into `log`, as `log` prints them; `none` files nothing; an index the log does not have is refused and nothing is closed). List only what is still open at close **and** is a defect Jori could not fix. The log is append-only, so leave out an `unresolved` entry a later entry fixed, a fix waiting on (or already given) the user's Face-ID signature, and a question waiting on the user's answer: none of those is a code defect for the system page, and the email lists them as open. Without `--still-open` it files every `unresolved` entry, those included.

**Applying the user's answer** (a run started by the user's reply): the user's words are final. Read them against every open question (`daily-summary-fix status <date>`, and the user's chat messages since the questions: several answers often arrive as separate messages seconds apart, or one reply answers several questions). Mark each question the user's words settle:
```bash
~/Dev/jori/bin/daily-summary-fix answered <date> <n> [<n> ...]     # n from `status`
```
That is your reading of what the user said, never a count of the user's messages; a reply that settles nothing settles nothing. Turn each answer into the record fix it implies (step 2), log it as `data-corrected` mentioning that the user answered, rebuild, review, and go to **Send**.

**The user's correction goes on top of the stored day, never over it (the user, 2026-10-22, D3).** Besides the record fix, record each answer that corrects the day in the user's words, with the window you read it as about:
```bash
~/Dev/jori/bin/day-correction add <date> --channel chat --said-at <the user's message's ISO time> \
  --text "<the user's words, verbatim>" --from <ISO with offset> --to <ISO with offset> [--reading "<your reading, one sentence>"]
```
That file (`data/day-corrections/<date>.jsonl`) is the corrected layer every later reader sees first: the rebuild's harvest, `location-day <date>` (each stop's `his_corrections`), `live-day day <date>`, and the wiki day page the publish refreshes. A name the user gave also goes through `findme resolve` / `location-confirm` as before (the row is what the map and resolve-day read). **Never edit `data/live-day-archive/<date>.json`**: it is what Jori believed during the day, and `live-day accuracy` grades it against the user's answers, so overwriting it would erase the measurement that finds these bugs.

## Send

**First, the gate.** Every send goes through it, the first send and a correction alike:
```bash
~/Dev/jori/bin/daily-summary-fix gate <date>      # exit 0 = send now, exit 3 = hold; JSON on stdout
```
- **Exit 3 (`waiting_on_answers`, or `waiting_to_ask` when the only questions are still held for the user's quiet hours)**: questions are open and the user's answer window has not closed. **Do not send.** If this run changed the day, or the day has no `daily_summaries` row yet, publish the data only (`daily-summary.md` Step 5.1: `publish` and the bookkeeping upsert, nothing after it), so the day's memory exists while it waits and the watchdog does not rebuild it from scratch. Then stop and say "held for the user's answers until <hold_until_local>". The gate has parked the day `awaiting_<owner_id>`; you are started again when the user answers (the chat agent passes the user's reply) or when the window closes (the hourly sweep).
- **Exit 0**: send now. `reason` tells you why: `no_open_questions` (all answered, or none asked) or `window_closed` (the window passed, or the user asked for it now). With `window_closed`, send the best version: the closing section lists what is still open as waiting on the user's answer, and an answer that arrives later gets one correction.
- Anything else (the check itself failed): send. The summary is never withheld on a broken check.

The closing section comes from code, never from you: it lists what the review caught and what was done, from the fix log and the final review, and anything still open.
```bash
~/Dev/jori/bin/daily-summary-fix section <date> --settled <i,j,...|none> --into /tmp/daily-summary-<date>.html
```
`--settled` lists the `unresolved` and `asked` log entries (0-based indices, as `log` prints them) that a later entry settled: a finding fixed by a later run, a question whose answer was applied. The log is append-only, so without this they read "not fixed yet" / "waiting on your answer" beside the entry that fixed them. Never list an entry that is still open; one you leave out only shows as still open. The list is kept on the day, so Step 5's own `section --into` (and a later correction) renders the same section without repeating it. Over 15 items, the section keeps every open one and drops the oldest fixes.
Then run `daily-summary.md` **Step 5** exactly (publish the data with `daily-summary-build publish`, the bookkeeping upsert, then `digest-deliver`), and record it with `daily-summary-fix mark-sent <date>`. The morning's episode archive may have written the wiki day page from the data published while the day was held, and it writes a page only once, so refresh it: `~/Dev/jori/bin/wiki read day_<date> >/dev/null 2>&1 && node ~/Dev/jori/bin/wiki-day-write <date>`.

- **First send** (the state has no `sends`): Step 5 as written.
- **A correction** (it was already sent, and this run confirmed the day or fixed a high issue since): Step 5 with the subject `Day of <Weekday>, <Month> <D>, <YYYY> (corrected)`, no `--pointer`, and `--push "<Weekday>'s summary, corrected — in your inbox"`; then `daily-summary-fix mark-sent <date> --corrected`. At most one correction a day unless the user asked for another.
- **Deadline: code, not you.** The first question of a day opens its answer window: 11am the user's time the next morning, or 3 hours after the question when it is asked later in the day (a question after the send holds only the correction, for 3 hours). A question held through the user's quiet hours opens it when it is asked (measured from the sweep that found the user up, so a 3-hour window ends on a sweep), so the user gets the same time to answer; until then `gate` holds the email on a provisional window. The user can end the wait themself ("just send it"): the chat agent runs `daily-summary-fix release <date>`. When the window closes the sweep starts you and the gate says `window_closed`: send the best version, keep the loop going, and send the correction when it confirms. **Never send while the gate says hold, and never hold past it.** A day with no question open is not held at all: if it is still not confirmed 4 hours after the first request, send the best version.
- Confirmed and sent → `daily-summary-fix done <date> --status confirmed`.

## Guardrails

- The user's words outrank every resolver, every confirmed-by-proximity name and every model guess. The review's evidence order applies here too.
- Outbound: only `daily-summary-fix ask` (a question to the user) and Step 5's `digest-deliver` (the user's own email). Nothing to anyone else.
- Records change only through `findme resolve`, `location-confirm`, `daily-summary-build confirm-venue`. Code changes land only through `self-improve-auto-apply` or a Face-ID card.
- **Kernel files stay generic** (`agent/CLAUDE.md` § Kernel boundary). A code fix to a file listed in `system/kernel-manifest.json` carries no personal data: no names, places, dates or quotes from the day in a code comment or a kernel test (the finding goes in `--details`, the commit message and the changelog; a fixture built from a real day goes in a `*-local.test.mjs` file); a value tuned to this installation goes in `agent/local/config/`, behaviour only it needs in an `_ext/` hook. A new file is classified in `system/kernel-manifest.json` in the same change. Run `bin/kernel-guard` before landing. Auto-apply exit 8 names what it found: move it and resubmit once.
- Health and bank data stay within the rules of `agent/CLAUDE.md`. Never paste them into a question.
- Never weaken, skip or rewrite the review to get a `confirmed`. The reviewer decides; you fix.

## Failure modes

- `/tmp` artifacts missing → rebuild with `daily-summary-build prep <date>` first.
- **Started by the sweep for a day that has never been sent** (the window closed, or the last run ended without sending) → before sending, check the summary did not already go out unrecorded (a run that died right after `digest-deliver`): search the user's inbox for today's `Day of <Weekday>, <Month> <D>, <YYYY>` from the agent's own address (instance `agent_email`). Found → `daily-summary-fix mark-sent <date>` instead of sending it again.
- Started by the sweep at the window's close with nothing new from the user → re-read the user's messages since the questions (the user may have answered without the chat agent passing it on), apply anything the user said, then Send. The sweep also restarts a never-sent day whose last run ended without sending or asking anything (the 2-hour cap, a crash, Max signed out); either way it retries 2.5 hours later, and after three runs it gives up and says so on the system channel.
- The review cannot run (Max unavailable) → do not send a correction; stop. The next request or the hourly sweep retries.
- A code fix you need is a Face-ID card → log it `unresolved` ("waiting on your approval"), keep fixing the rest, send by the deadline with it listed as open.
