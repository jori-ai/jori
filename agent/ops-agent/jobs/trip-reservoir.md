TRIP RESERVOIR — Researches ONE location once into a vetted 5-bucket travel guide (reservoir) of places, food specialties, unique experiences, and time-sensitive events (festivals, fairs, markets), stored as JSON + a wiki page and served on the travel site. Blueprint: `data/reviews/trip-planning-agency-2026-07-09.md`. Methodology: the `itinerary-planning` skill.

## Purpose

A good trip starts with knowing what a place *offers*. This job builds that standing candidate list per base: must-see + optional places (each with its local-food hook), the region's must-try food specialties mapped to the best place for each, unique experiences (a sunset spot, a sailing), and time-sensitive events (**festivals, fairs, and markets — hunted explicitly**, after a nearby medieval-festival near-miss) with their timing constraints. Every place is Google-Places-verified at capture; anything that won't resolve is dropped. This is the durable travel guide for a place. It accumulates learning — the site's Done/Skip pills and the nightly `trip-reservoir-mark-done` sweep mark entries so the guide reflects where the user has actually been and what they've ruled out.

## When it runs

**Automatically, for any upcoming non-home location — with no agent turn.** The nightly launchd user agent `ai.claude.trip-reservoir-autoscan` (02:00 local) runs `trigger-trip-reservoir-autoscan.sh`, which reads the travel timeline (`trip-reservoir-autoscan --check / --list`) and runs `trip-reservoir-build --area <key> --label "<label>" --from <from> --to <to>` for each upcoming non-home stay with no guide, **one at a time** (5 concurrent Sonnet forks exhausted the Max pool on 2026-07-09). It runs under launchd rather than cron because the build forks a Sonnet `claude -p` that needs the keychain-held Max session; until 2026-10-04 cron worked around that by dispatching an ops turn whose only work was that loop. Home bases (travel.json `home_metros` and their aliases, plus trip-planning.json `home_metros`) and short layovers are skipped. Log: `agent/logs/trip-reservoir-autoscan.log`. Photos are filled by the nightly `trip-reservoir-mark-done` sweep.

You can also build one on demand for a specific place at any time (see Pipeline).

## Pipeline

**Launch as a protected background job — the research fork takes minutes and must not tie up or be orphaned by the ops session.** (It is a **Sonnet** fork, not Opus — see step 1 below.) See `agent/CLAUDE.md § Long-Running Jobs`.

```bash
~/Dev/jori/bin/job-run --name trip-reservoir -- \
  ~/Dev/jori/bin/trip-reservoir-build --area <leg> [--from YYYY-MM-DD --to YYYY-MM-DD]
```

Then end the turn with a one-line ack. `trip-reservoir-build` does everything itself: Sonnet-fork research of the 5 buckets → Places-verify every named place → carry forward any prior done/skipped/felt/photo annotations → write `data/trip-reservoir/<area>.json` + the `trip_reservoir_<area>` wiki page. Exits 0 on a written reservoir, 1 on research failure (it posts its own `⚠️ trip-reservoir-build:` system-channel alert first — do not post a second), 2 on a no-op (nothing verified). Test a script change with `--dry-run` (runs the real research fork + verify but prints the reservoir instead of writing).

**Size scales with the stay (2026-10-02).** With a `--from/--to` window the research prompt asks for a total entry TARGET from `lib/reservoir-target.js` — a power law through two anchors (1 day → 10–15, 30 days → ~120): 1d ≈ 13 · 3d ≈ 26 · 7d ≈ 46 · 14d ≈ 72 · 30d ≈ 120, so per-day density falls as the stay lengthens. The prompt gets a ±15% range plus a rough bucket split (food + optional ~35% each, must_see / experiences / time-sensitive ~10% each) and is told it is a target, not a quota — return less if the area offers less, never pad. The research fork's timeout scales with it (~12s per targeted entry, floor 10 min). No window → no number (unchanged behavior).

**Long stays research in ROUNDS; `--top-up` grows a guide in use (2026-10-02).** The curve keeps going past 30 days (60d ≈ 196, 90d ≈ 257), but one Sonnet fork can't reliably return 200+ entries, so a target above 60 is researched in rounds of ≤60, each prompt listing what the guide already holds ("do NOT return these again"). Rounds research toward the TOP of the range (`target.high`), because verification + dedup drop ~15–20% of raw research (one top-up: 69 found → 57 kept, landing at 89 against 95–129). Rounds stop when that is met, when a round adds <5 new names (area tapped out — never pad), or after ⌈high/60⌉+1 rounds. Each round is checkpointed (`research_complete:false` until the last), so a killed build resumes mid-rounds. `trip-reservoir-build --area <key> --top-up` keeps EVERY existing entry untouched (ids, done marks, photos) and researches only the gap to the stay target (window taken from the stored `date_range` if `--from/--to` is omitted); exits 2 if already at target. Use it instead of a rebuild for a guide that's already in use mid-trip — a rebuild drops anything it doesn't re-find. First used on a 41-entry guide (target ~112).

**Research is PASS 1 of three (2026-07-20).** The build now runs two more passes over the finished reservoir before it persists, both in `lib/reservoir-refine.js` so a fresh build and a backfill do the same thing:

- **Pass 2 — dedup** (`lib/reservoir-dedup.js`). One research prompt asks for five buckets at once, so the same venue landed in `must_see` AND `optional` AND as a food `best_place`, and the same food repeated. Venue identity is the resolved `mapsUri` (or <75m + a similar name); dish identity is the normalized dish HEAD phrase — `dish` is a *description* ("Pâté de Townsville (pâté en croûte of game — …)"), so comparing whole strings found 1 duplicate across 382 entries and the head finds 9. **Non-destructive:** a loser keeps its row with `state:"duplicate"` + `dup_of`, so `carryAnnotations` still carries its done mark and a wrong merge is recoverable — every renderer filters `state==="duplicate"` instead. A dish and the sight it sits inside are NOT merged; they're linked by `same_venue_as` so the map draws one pin. Pairs that are similar-but-uncertain go to ONE bounded Sonnet call (`--effort low`, names only, no web search); if it fails, the deterministic dedup stands alone.
- **Pass 3 — clusters + numbering** (`lib/reservoir-cluster.js`). Groups entries into walkable pods (1.2km) and marks each **walk** or **drive Nkm** by distance from the base (2.5km threshold — at 1.5km, city clusters 1.8km out read as "drive"). Generalizes `clusterSights()` from the since-retired `france-itinerary-layout` so both callers shared one implementation. Also assigns **`seq` 1..N**, which the site list, the map pins and the wiki renderer all read, so three renderers can't drift into three numberings — and **regenerates `dont_miss`**, which nothing had written since its origin script was removed (every rebuild silently dropped it and the itinerary lost its hero ranking).

**Backfilling an existing area:** `trip-reservoir-publish --refine` re-runs both passes over the stored reservoir without re-researching it (add `--no-resolve` to skip the model call entirely). That's how the 7 existing areas got clusters and numbers.

**`food_specialties` entries are one of TWO kinds, and the distinction is load-bearing (2026-07-21).** Every entry declares `kind`: a **`"dish"`** carries a canonical food NOUN in `dish` (`"Kouign-amann"`, `"Navarin d'agneau"`) and is photographed with a picture of THAT FOOD; a **`"table"`** is a local restaurant recommended for itself, carries `dish: null` + a `known_for` style blurb, is headlined by the restaurant name in all three renderers, and is photographed with a picture of the RESTAURANT. Before this split both shapes shared the `dish` field — the prompt literally told the model to put `"cuisine familiale / plat du jour"` there — so 81 of 129 photographed food entries were keyed on a menu blurb, which no image source can answer. Every source returned its nearest coincidence instead (a photo of a fishing town for `"sardines grillées…"`, stock sushi for `"Fresh landed fish and seafood"`). The prompt also enforces **one entry per dish** — repeated seafood wordings are one dish, not six. If you touch the food bucket, keep `kind` populated; a row with neither marker is read as a table.

**Photos are a SEPARATE pass, run after the research (added 2026-07-17).** The builder verifies places but does not fetch images; `bin/trip-reservoir-photos` does, in its own pass — for each entry without a `photo_url` it re-hosts a photo into Supabase storage (never a Google URL with a live API key in it) and writes `entry.photo_url` + `entry.photo_source`. A place or a **table** gets its Google Places photo. A **dish** goes down a verifiability ladder and never touches Unsplash (`--wiki-only`): gated Wikipedia article → gated Wikimedia Commons file search → Google image search (last resort, inert unless `GOOGLE_CSE_ID` is set; the cx must be created once at programmablesearchengine.google.com with the Custom Search JSON API enabled). The first two rungs reject any hit that has `coordinates` (a page with a location is a place, not a dish), lacks a food category, or whose title doesn't resemble the query. **A dish we can't verify gets NO photo — that is the correct outcome, not a failure.** It's idempotent (entries that already have one are skipped) and photo failures are skips, not job failures. The nightly `trip-reservoir-mark-done` sweep runs it automatically so a freshly-built or newly-added entry gets a picture without a manual pass; run it by hand (`trip-reservoir-photos --area <leg>`) right after building a new leg if you don't want to wait for the nightly. Photos survive a rebuild via carryAnnotations.

For an ad-hoc area not in the builder's preset areas (trip-planning.json `areas`): `--label "<area>" --lat <n> --lon <n>`.

### What the builder does (for reference / debugging)

1. **Sonnet-fork research** — `claude -p --model claude-sonnet-5-5 --effort medium --allowedTools WebSearch`, forked from the already-Max-authenticated parent (via job-run), prompted for the 5 buckets weighted by how the travellers travel (trip-planning.json `travellers` + `research_style`; coastal-towns/markets/old-quarters default, crowds only if iconic, museums/churches only if must-see; a preset area with `localOnly` and any `--local-only` build skips tourist highlights entirely and surfaces only local favorites). Strict JSON out. **Dining is searched in the LOCAL LANGUAGE** (French in France, and so on) and targets the pleasant, family-run, welcoming, blue-collar, *locals-recommend-to-locals* restaurants — bucket 3 (`food_specialties`) carries both the dish→best-place canon AND a handful of everyday local family tables; the configured style decides how fine dining is weighted. Restaurants are the priority; a genuine local coffee shop is a bonus, not required. (Prompt strengthened 2026-07-11.) This is **Sonnet, not Opus** — building a reservoir is web-search + summary, so Opus xhigh is overkill; the same cheap-subagent tier the Effort Policy prescribes for the hum harvesters.

   **Resumable (2026-07-09):** the parsed research is checkpointed to `data/trip-reservoir/.<area>.ckpt.json` the instant it succeeds, and verified entries are checkpointed every 5, so a run killed mid-verify **resumes** (reusing the research + already-verified entries) rather than re-forking. The checkpoint is deleted on successful completion.

   **Build SEQUENTIALLY, not concurrently.** Running 5 area builds at once exhausted the Max pool on 2026-07-09 and killed every build but the first. Launch one leg, let it finish (~5-15 min on Sonnet), then the next — or a small controlled batch, never the whole trip at once.
2. **Verify + resolve** — every named place goes through `trip-place-verify "<query>" <lat> <lon>` (direct Places Text Search biased to the base). Resolved → attach mapsUri/address/rating/lat/lon; unresolved → drop (except a unique experience with no fixed location, which may legitimately have no venue).
3. **Carry annotations** — on a rebuild, prior `state`/`skip_reason`/`felt` are preserved by name so feedback isn't lost.
4. **Write** — JSON state file (machine source of truth) + a browsable `trip_reservoir_<area>` wiki page (readable via `wiki_read`).

## State file

`data/trip-reservoir/<area>.json` — one per base/area, gitignored (trip-specific, not meaningful after the trip). Schema in the blueprint doc. Written by this job; read by Phase 2 (the `trip-day-plan` skill, `trip-day-select`, `trip-reservoir-status`) and annotated by `trip-feedback`. Wiki mirror: `trip_reservoir_<area>`.

## Guardrails

- **Read-only research.** No sends, no bookings, no money. Never emails the travellers — that's Phase 2's job.
- **Never invent a place, market day, or event date.** Places-verify at capture; a dated one-off with no confirming source is omitted (`null`/drop beats a guess). Same hallucination discipline the earlier itinerary pipeline was held to.
- **Presence-gated.** Only build for areas the travel timeline places them in (`travel in-city`), consistent with the mandatory event geo-gate.
- **Silent on skip, loud on failure.** A no-op (nothing verified) exits 2 silently; a research failure exits 1 after its own system-channel alert.

## Failure modes

- **Sonnet research fork fails after 2 attempts:** alert via system channel, exit 1, write nothing — next run retries.
- **Places verification finds nothing for any bucket:** exit 2, write no empty reservoir.
- **Wiki write fails:** non-fatal — the JSON (the source of truth) is already written; log and continue.
- **Script bug (not transient):** fix `bin/trip-reservoir-build`, verify with `--dry-run`, do not hand-run the research in a conversational turn.
