# Conversations with the team

The app is a messenger with the user's team (system/org.md): every role is a "person" the user can talk to, like a contact in a messaging app. The coordinator (the chief of staff, the assistant itself) is there from the start; a role appears once it has something to say or the user adds it; the user can @mention roles into a conversation, start groups of several, and rename any role.

## Data (migration 0180, Supabase)

| Table / column | What it holds |
|---|---|
| `jori_team` | One row per role: `id` (the role plugin's id), `name`, `title`, `responsibility`, `chief_of_staff`, `enabled`, `sort`, `renamed_by_user`. `org sync` (every 10 min) writes it from the roster; the app writes `name`/`title` when the user renames a role, and sync keeps those. |
| `jori_conversations` | `role:<id>` (one role) or `group:<uuid>` (`members` = role ids, `title`); `last_message_at`, `archived`, `created_by`. |
| `jori_channel_roles` | The role that answers for each legacy channel: chat and questions → the coordinator, system and improvements → Product (all the tech; system was IT & Security's until migration 0187). |
| `jori_messages.conversation_id`, `.sender` | Where a message belongs and which role wrote it. |

Triggers: a row that names only a channel (or only a `sender`) is filed in the matching role's conversation, and `channel` stays meaningful for the older app; a role's conversation is created by its first message; `last_message_at` follows every insert.

## Writing to the user

- **Jobs** (`jori-send-curl`): the role that owns the job (or `--role <id>`) goes on the row as `sender`, so it lands in that role's conversation. The coordinator's own messages (digests it owns) stay in its conversation. Emails and pushes are signed by role (system/org.md).
- **Hum pings go to the member whose area they are about** (2026-11-20). Hum is the coordinator's job, but `bin/hum-ping` asks `bin/ping-route` (`lib/ping-route.mjs`) which member a ping belongs to and sends it with `jori-send-curl --as-role <id>`: that member's conversation, signed `Name: …` like their own jobs' pings, the push titled `Name (Title)`. The router is a model: Jev site `ping-route` (one choice over the team, built per call from the roster), the Haiku → Sonnet → Opus ladder below its threshold. **Bank and health content never reaches Jev**, whatever `privacy_exclusions` says: a ping on a private lane or intent (finance, stocks, health, exercise, the installation's private intent prefixes) is decided by the ladder alone, and every other ping is read first by the on-device screen (fail-closed). Location questions and pings carrying a tappable card stay with the coordinator (the chat agent records those answers), and so do local explanations (`nearby`: where the user is, worth something only while they are there, so never delayed by a model) and any ping the router cannot settle within 40 s. A reply typed in the member's conversation is answered by that member's session, and hum still learns from it: `bin/role-session prepare` finds the hum ping it answers (`lib/hum-reply-target.mjs` `routedPingReply`: its `reply_to`, else the last assistant message before it in that conversation when that is a hum ping from the last 6 h), runs the reaction classifier (`bin/suggestion-classify --reply-to`) pinned to it, and gives the session hum's filing line (`[Hum routing]`: `jori hum feedback <ping> <token>` or the ping's `watchlist …` command; `jobs/role-session.md`). Tapback reactions reach hum's feedback from any conversation. Hum questions (`hum-ask`) stay with the coordinator. Log `data/ping-route-log.jsonl`; off switch `data/.ping-route-off`.
- **Questions** follow the same rule: a question lives in the conversation of the role whose job asked.
- **Replies** in the coordinator's conversation come from the chat agent (phone-channel `reply`), written into the conversation the user wrote in.
- **A job started for a request answers where it was asked** (2026-11-18; the owner: "car price request should go back to the channel that requested them"). The asker passes `--reply-to <conversation id>` to `jori tasks run` / `jori dispatch` (`lib/reply-to.cjs` adds a `Reply to: conversation <id>` line to the task). The job then sends with `jori-send-curl --conversation <id>`, which writes `conversation_id` on the row, so it lands in that conversation, still signed by the job's role (`agent/ops-agent/CLAUDE.md` § Scheduled Jobs). The chat agent reads the id from the `[Conversation: …]` line phone-channel adds to each message; a role session has it in its task.
- **No background helpers outside the chat agent.** `delegate` and `check_later` are drained only by the chat supervisor, so tools-mcp offers them only where `JORI_AGENT_ID` is `chat` (`agent/tools-mcp/profiles.mjs` `servesLoopTools`). Before that an unset id meant `chat`, so a role's research ran under the chat agent and its answer went to the coordinator. A role does the work in its own session or starts a job.

## The user writing to a role

phone-channel (`teamRoute`) decides who answers a user message:

- a message that @mentions roles (`metadata.mentions`, "a,b", set by the app from `@name`), in ANY conversation: each mentioned role answers in that same conversation on its own session; the coordinator answers too only when mentioned. The mention brings them into the conversation (they join its `members`); no new group is started (the user's call, 2026-11-10). A role joining someone else's conversation is told so, and reads its last 30 messages before answering;
- otherwise, in `role:<coordinator>` (or no conversation): the chat agent, as today;
- in `role:<id>`: that role's own session;
- in a group with no mention: the coordinator.

A role's message is queued at `data/role-queue/pending/<time>-<message id>.json`; launchd `ai.claude.role-session` (QueueDirectories, from the role-chief-of-staff plugin) runs `plugins/role-chief-of-staff/bin/role-session-trigger`, which for each role runs `agent/ops-agent/jobs/role-session.md` through `lib/run-ephemeral-opus.sh` on Sonnet at medium effort, with a task built by `bin/role-session prepare` (the role's specialization, the conversation's last 30 messages with names, the new message). The role answers with `bin/role-session reply` (sender = the role, a push titled with its name and title).

**Each role has its own session** (the user's choice): the fork resumes the role's last session (`JORI_FORK_RESUME`, recorded in `data/role-sessions.json` through `JORI_FORK_SESSION_OUT`) and starts a fresh one after 30 turns or 12 idle hours, because every resumed turn re-reads the whole session. The conversation's recent messages are in every task, so a fresh session loses nothing the user sees. Role sessions carry every rule in `agent/CLAUDE.md`; a role is a specialization of Jori, not a separate permission.

## Answers to open questions: filed by code, in whatever conversation the user answers

A job's question lands in the conversation of the role that owns the job (`jori-send-curl` places it; hum pings go to the member whose area they are about), but the filing of its answer used to be the coordinator chat agent's alone. On 2026-11-21 the daily summary's questions about the 20th went to the software engineer's conversation, the user answered there, the role session had no step to file it, and the day stayed `awaiting` with no answers and the summary held. Now `lib/answer-router.mjs` files it, for every inbound user message in every conversation (a role's, a group's, the coordinator's):

1. **phone-channel** starts `routeAnswer` the moment a message arrives (after the tap fast path), in parallel with everything else; the coordinator's turn waits for it up to 3 s to learn what was filed, a role's message is never held up.
2. Each **flow** lists the questions it is still waiting on; **a model reads the message against them** (Rule #0b; Haiku → Sonnet → Opus, a rung climbed only when the one below throws or gives no valid reading) and names the ones it answers; the flow files the user's words, verbatim, once. The flow decides what the words settle: the fixer reads them against its own questions, so a partial or oblique answer is still passed on.
3. **Idempotent per message id** (`data/answer-router/<message id>.json`, claimed with O_EXCL): the hook, `bin/role-session prepare` (the playbook-side fallback, which also waits for the hook's outcome and tells the role "answer already filed, acknowledge it") and the coordinator filing it by hand all collapse into one filing. `daily-summary-fix request --answer` also ignores an answer already recorded (same `--message-id`, or the same words within 15 minutes).
4. Fails open: no model reading (not logged in, usage limit) means nothing is filed and the agent handles the message as before; an error while filing drops the claim so the next caller retries. Kill switch: `data/.answer-router-off` (or `ANSWER_ROUTER_OFF=1`).

**Flows that file in code:** `daily-summary-fix` (`bin/daily-summary-fix open-asks` lists every question asked and not answered in the last 72 h, evening-pass questions included; filing is `request <date> --answer <words> --message-id <id>`, which queues the fixer) and `hum-question` (the plain questions in `data/open-questions.jsonl`, filed with `hum-answer <id> "<words>"`; not the location lanes, the self-re-asking lanes or the `hum_improvement:` offers). An installation adds its own in `lib/_ext/open-ask-flows.mjs` (`export const flows = [{ id, list(), file() }]`).

**The audit of every other flow that waits for an answer** (2026-11-21), after the same gap:

| Flow | Where it asks | How its answer is filed | Gap, and what was done |
|---|---|---|---|
| Daily-summary fix questions | the owning role (the product role) | fixer `request --answer` | **Was the bug; fixed above.** |
| Hum pings and questions (plain) | the member whose area it is | `hum-answer` / `jori hum feedback` | A reply in the member's own conversation had a HUM block (role-session, from the last 30 rows); a reply in a group, an @mention elsewhere, or to a question older than those rows had none. **Fixed:** plain open questions are filed by `hum-question`. |
| Hum questions that offer to change hum (`hum_improvement:`), and the location lanes | coordinator (location, cards, and anything unrouted stay there by design) | chat agent: `hum-idea-decide` (needs a reading of go-ahead / twist / refusal), `findme resolve` | **Listed, not automated:** the answer must do more than land in a ledger, so an answer typed outside the coordinator's conversation is read by a role that has no procedure. Keeping these in the coordinator's conversation is what makes them work; a stray reply elsewhere is the residual gap. |
| Decision cards and build-park questions | coordinator, or the role the source names (`decision-ask --role`) | a tap: `choice-reply` in code, any conversation; a typed reply: the agent, from a `[Decision card]` / `[Build question]` line | **Fixed:** that line is now `lib/card-reply-hint.mjs`, used by phone-channel and by `role-session prepare` (a `----- CARD REPLY -----` block when the reply is threaded to a card). | Watches (`watch ask`) and purchases' Face-ID approvals | coordinator; approvals are a signature, not words | the watch engine / `bin/approval` | No typed answer is involved in a role conversation; nothing to file. |

## The app

`apps/companion`: a conversation list (each row: names with their role titles, the last message, and a single red badge counting unread messages, unanswered questions and Face ID approvals — no icons, nothing when nothing is waiting; counted by one query for the whole list, and a question or choice card with no expiry of its own stops counting after 30 days; the list fetches only questions with no recorded answer), a conversation view filtered by `conversation_id` with the sender's name and title on each message in a group, `@name` autocomplete that brings a role into the conversation on screen (and sets `metadata.mentions`), new groups from the new-conversation sheet, a photo per role (tap its avatar in the people sheet: the picked image is shrunk to a 512 px JPEG, uploaded to the attachments bucket under `team/`, and its URL stored in `jori_team.avatar_url`, migration 0182, which org sync never overwrites; the initials stay the default and "Use initials instead" goes back), and renaming a role's name and title. Deleting a conversation or a group (swipe, or right-click / long-press, then confirm) archives it (`jori_conversations.archived`): it leaves the list, its messages stay in Jori's memory, a role's own conversation comes back when that role next writes (the touch trigger un-archives `role:` conversations), and a deleted group stays gone. The coordinator's conversation can't be deleted. Any conversation, the coordinator's included, can be pinned to the top of the list like iMessage (right-click / long-press › Pin, or swipe right on iPhone/iPad): `jori_conversations.pinned_at` (migration 0183) — pinned conversations show as a grid of big circles above the list, three across with the name and role under each (each cut to 16 characters, in a small font) and a red badge when something waits (`PinnedConversationsGrid`), in the order they were pinned, synced across devices; right-click / long-press a circle to unpin; the app falls back to an unpinned list on a database without the column. On the Mac, hiding the sidebar folds it to a rail of avatars with names (`ConversationRail`: pinned first, a short rule, then the rest; the open one on a blue tile) instead of removing it, and the window shrinks by the sidebar minus the rail. The Mac lays sidebar/rail and conversation out itself (an HStack with its own ⌃⌘S toggle in the toolbar), not in a NavigationSplitView: the split view's collapse animation, the rail and the window resize ran on separate clocks and left a gap and a blink; now the swap and the window resize happen in one pass with no animation, so the conversation keeps its width. The sidebar has no Library section: Memory is in the Go menu (⌘2); on the iPhone it is in the list's … menu, not a toolbar button. The channel menu is gone: channels are roles' conversations. Reopening the app comes back to the screen it was left on: the open conversation, Memory (on the wiki page last open, while it is on the same wiki host; `memoryLastPage`) or the software engineer's improvement cards, the iPhone inside that conversation rather than on the list, and on the Mac a sidebar the user folded stays folded (one folded by narrowing the window folds again by itself) — kept in UserDefaults (`currentConversation`, `memoryOpen`, `improvementCardsOpen`, `phoneInDetail`, `sidebarFolded`, `windowShrunkForSidebar`).
